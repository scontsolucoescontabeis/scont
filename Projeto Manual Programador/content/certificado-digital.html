Certificado Digital vive em Projeto Certificado Digital/ e é uma SPA de página única: todas as telas (Dashboard, Certificados, Relatórios, Agenda, Histórico, Segurança, Configurações) são <section class="page"> dentro do mesmo index.html, alternadas via setPage() — não existe um arquivo HTML por tela como em outras ferramentas do portal. Stack: HTML + JS puro, sem framework/bundler, IIFE global (APP_STATE como estado único). Cliente Supabase único criado em js/config.js (supabaseClient), autenticação via portal-auth-guard.js compartilhado do portal, orquestrada por js/auth.js (checkAuth()). Toda a lógica de tela, CRUD e renderização está em js/app.js (~1465 linhas); js/utils.js tem formatação/validação/toasts; js/config.js declara constantes, nomes de tabela e o estado global. Não há geração de PDF nesta ferramenta (diferente de outras do portal) — Relatórios exporta CSV client-side e a importação em massa usa SheetJS (xlsx) via CDN. Ignore certificado_digital.html solto na raiz da pasta — é um prototípo antigo isolado, só com localStorage, sem nenhuma integração com Supabase; a ferramenta real é index.html + js/*.js. Não há build step — arquivos servidos como estão.

Dashboard

Decisões de Design / Particularidades

  • Padrão situacaoEfetiva — leia antes de tocar em qualquer lógica de situação. Até 2026-08-10 a coluna situacao só era reescrita manualmente (cadastro/renovação/agendamento): um certificado "Ativo" nunca virava "Vencido" sozinho quando a data passava, porque nada recalculava a coluna com o tempo. A correção foi situacaoEfetiva(cert) em js/utils.js — recalcula Ativo → Vencido comparando data_vencimento com hoje só no momento de exibir/filtrar (dashboard, tabela, relatório, agenda, CSV, filtro por situação). Ela não reescreve a coluna no banco e não altera o formulário de edição — o campo "Situação" do modal (openCertModal) continua mostrando cert.situacao cru. Os demais estados (Agendado, Renovado, Aguardando Contato) são de workflow e não são tocados por essa função. Qualquer tela nova que liste/filtre certificados precisa chamar situacaoEfetiva() em vez de ler cert.situacao direto — é fácil reintroduzir o mesmo bug adicionando uma tela que esqueça disso (ex.: um card novo, um export novo).
  • Checkbox "inativo" no formulário é invertido em relação à coluna: o campo do banco é ativo (true = ativo), mas o checkbox #ativo marca inatividade ("Cliente/certificado inativo..."). saveCertificate() grava ativo: !(checkbox marcado), e openCertModal() faz o inverso na carga (checked = cert.ativo === false). Um id de campo igual ao nome da coluna com semântica oposta é uma armadilha clássica de leitura rápida do código.
  • canRenew(cert) (limiar de 60 dias) controla tanto o botão "♻ Renovar" na tabela/detalhes quanto a divisão da tela Agenda entre "agendados" e "vencimentos próximos sem agendamento" — mesmo limiar, duas telas.
  • Exclusão em lote (deleteSelectedCerts) faz um UPDATE por id em sequência (sem Promise.all, sem batch), reportando sucesso/falha por item — lento para seleções grandes, mas cada falha individual não impede as demais.

Dívida Técnica / Pendências

  • Tabela certificados não tem CREATE TABLE nem definição de RLS de SELECT/UPDATE/DELETE versionada em nenhum arquivo do repo — só as colunas adicionadas depois por migração incremental. Qualquer alteração estrutural feita direto no painel do Supabase fica invisível pro Git.
  • TABLE_NAMES.EMPRESAS, TIPOS, AUTORIDADES, ALERTAS, AGENDA, LOGS, INTEGRACAO, NOTIFICACOES, RELATORIOS (em js/config.js) e BUCKET_NAMES.CERTIFICADOS nunca são referenciados em nenhum .from()/.storage. do código — nomes reservados de um modelo mais normalizado que nunca foi implementado. Não há upload de arquivo nesta ferramenta apesar do bucket declarado.

Agenda / Renovação

Stack e Estrutura de Arquivos

  • Dois modais compartilhados com a tela Certificados: #scheduleModal (agendar/reagendar) e #renewModal (concluir renovação), abertos também a partir da tabela de Certificados e do modal de Detalhes.

Modelo de Dados

Sem tabela própria. Usa exclusivamente certificados.data_renovacao_agendada, data_vencimento, data_emissao, situacao e ultimo_alerta_nivel (ver seção Certificados). Toda renovação concluída grava uma linha em historico_certificados (ver seção Histórico).

Fluxo Principal

stateDiagram-v2
    [*] --> SemAgendamento
    SemAgendamento --> Agendado: saveSchedule grava data_renovacao_agendada e situacao Agendado
    Agendado --> SemAgendamento: removeSchedule limpa data e recalcula situacao Ativo ou Vencido pela data

Decisões de Design / Particularidades

  • removeSchedule() recalcula a situação na hora (Vencido se daysLeft < 0, senão Ativo) e grava direto no banco — é uma reescrita manual pontual, não o padrão situacaoEfetiva() (que é só de exibição). Ou seja: aqui a coluna é corrigida na base, porque a ação do usuário (remover agendamento) é o gatilho natural para persistir o novo estado.
  • O e-mail de "alerta resolvido" só é disparado no fluxo manual de renovação — não existe uma verificação periódica que resolva alertas de certificados renovados por outro caminho (ex.: edição direta do campo data_vencimento no modal de Certificados não passa por saveRenewal() e não reseta ultimo_alerta_nivel nem envia esse e-mail).

Decisões de Design / Particularidades

  • O gate de permissão só protege a tela Segurança — não protege o modal de edição. openCertModal() (tela Certificados, disponível a qualquer usuário com acesso à ferramenta) faz q('#senha').value = cert.senha_hash direto, sem checar APP_STATE.podeVerSenha. Ou seja: qualquer usuário que consiga abrir "✏ Editar" em um certificado com senha cadastrada vê a senha em texto simples no campo do formulário, independentemente de ter a sub-permissão ver_senhas. O RPC gated por permissão é real, mas o caminho de edição contorna ele por completo — isso não é um bug sutil de RLS, é um caminho de leitura que simplesmente não passa pelo controle de acesso. Qualquer revisão de segurança desta ferramenta precisa considerar os dois caminhos.
  • O rótulo da coluna/RPC ("hash", "decifrar") sugere criptografia forte, mas por padrão (chave do Vault vazia) o dado é reversível com atob() por qualquer um com acesso direto à tabela via service role — documentado explicitamente como risco alto no comentário de _sql/lgpd_compliance_migration.sql, seção de avisos.

Dívida Técnica / Pendências

  • Migrar cert_encryption_key do Vault de valor vazio para uma chave real (ativando pgp_sym_encrypt nas gravações futuras) é uma ação manual pendente — hoje o sistema funciona inteiramente no modo fallback base64/texto puro.
  • Fechar a brecha do modal de edição (não popular #senha com o valor cru para quem não tem ver_senhas, ou trocar por um placeholder + fluxo de "trocar senha" que não expõe a atual) não foi implementado.

Decisões de Design / Particularidades

  • daysLeft() é reimplementada de forma independente em três lugares com a mesma lógica: js/utils.js (front, fuso local do navegador), a Edge Function do cron (Deno, fuso UTC explícito via Date.UTC) e implicitamente nos comentários do SQL. O comentário no topo da função na Edge Function deixa isso explícito ("mesma lógica... usada no frontend") — mudar o critério de "dias restantes" em um lugar sem replicar no outro gera divergência entre o que o app mostra e o que dispara o e-mail.
  • Limiares de alerta (ALERT_CONFIG) têm defaults hardcoded no front (7/15/30 dias) que só são sobrescritos depois que loadConfiguracoes() resolve — a Edge Function usa os mesmos defaults como fallback (cfg.dias_critico || '7'), então os dois ficam consistentes mesmo se a tabela estiver vazia.
  • O JWT anon key usado pelo net.http_post do cron está hardcoded em texto claro dentro de schema_certificado_alertas_cron.sql — é a anon key pública do projeto (não a service role), então o risco de exposição é baixo, mas ainda é um valor específico de ambiente cravado num arquivo versionado; reexecutar esse script em outro projeto Supabase exige editar a URL e o JWT manualmente.
