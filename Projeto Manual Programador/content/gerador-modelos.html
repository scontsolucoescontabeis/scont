O Gerador de Modelos vive em Projeto Gerador Modelos/: um único par index.html (~600 linhas, todas as telas como <section> alternadas por showSection()) + app.js (~2150 linhas, sem módulos/IIFE — tudo em escopo global). HTML + JS puro, sem framework/bundler, cliente Supabase próprio (supabase-config.js + portal-auth-guard.js compartilhados do portal). Bibliotecas via CDN: xlsx.js 0.18.5 (leitura/escrita de planilhas), html2canvas 1.4.1 e jspdf 2.5.1 — as duas últimas carregadas no index.html mas não usadas em nenhum ponto do app.js (confirmado por grep; nenhuma chamada a html2canvas( ou new jsPDF( no arquivo). A exportação "PDF" de verdade é feita abrindo uma janela nova com window.open e disparando window.print() — o usuário salva como PDF pela própria caixa de impressão do navegador. O módulo gira em torno de um "wizard" de 7 passos possíveis cuja sequência real é recalculada dinamicamente a partir das fontes de dados marcadas no modelo (ou na união dos modelos de um Evento).

Modelos

Stack e Estrutura de Arquivos

  • index.html — seção #modelos (grid de cards) + modal de edição (#modal-modelo) com editor rich-text via contenteditable (sem biblioteca de editor — barra de formatação própria usando document.execCommand) e alternância "Ver HTML" (toggleModoHtml()) para editar o template como texto puro.
  • app.js — CRUD em carregarModelos()/renderModelos()/salvarModelo()/deletarModelo(); painel de variáveis em renderVarsPanel()/insertVar(); catálogo de variáveis disponíveis por fonte é a constante VARS_DEF (objeto estático no topo do arquivo, ~200 linhas — empresas/empregados/socios/rubricas/excel/sistema, cada uma com prefix e lista [campo, label]).
  • Upload de planilha extra dentro do modal do modelo usa as mesmas funções de parsing Excel do wizard (handleExcelUpload/_normalizeExcelData), mas grava o resultado no template/estado do modelo, não no wizardRegistros.

Modelo de Dados

TabelaColunas-chaveObservações
gm_modelosid, nome, descricao, tipo (CHECK por_registro/consolidado), template (HTML com {{variavel}}), cabecalho_padrao (CHECK completo/neutro/nenhum), fontes (TEXT[], subconjunto de empresas/empregados/socios/rubricas/excel), criado_porRLS: SELECT aberto a qualquer autenticado; INSERT/UPDATE/DELETE restritos a is_admin() OU auth.uid() = criado_por.

Fontes externas lidas (não pertencem ao Gerador de Modelos): rh_empresas, rh_empregados, rh_socios, rh_rubricas — todas do módulo RH, consultadas direto por codigo_empresa, sem tabela de junção própria.

Fluxo Principal

substituirVars(template, varMap, highlight) faz a interpolação com template.replace(/\{\{([^}]+)\}\}/g, ...). Prefixo extenso: antes da chave (ex.: {{extenso:empregado.salario}}) desvia para valorPorExtenso() em vez do valor bruto — é essa a implementação por trás do botão "ext" ao lado dos campos numéricos no painel de variáveis (o botão só insere o texto {{extenso:...}}, não existe estado de "modo extenso" separado). Quando highlight=true (usado só na pré-visualização), uma variável sem valor no varMap é envolvida em <span class="var-missing"> em vez de sumir; na exportação real (highlight=false) uma variável sem valor mantém o texto literal {{...}} no documento final.

flowchart TD
    A[Usuario marca fontes de dados] --> B[VARS_DEF libera grupos de variaveis no painel]
    B --> C[Clique na variavel chama insertVar]
    C --> D[Insere texto na posicao do cursor do contenteditable]
    D --> E{Campo numerico}
    E -- sim, botao ext --> F[Insere prefixo extenso antes do campo]
    E -- nao --> G[Insere campo puro]
    F --> H[salvarModelo grava template em gm_modelos]
    G --> H

Decisões de Design / Particularidades

  • Tipo "Consolidado" não é por empregado: apesar do rótulo na UI ("um documento por empresa, reunindo todos os registros"), o código de construirRegistros() (linha ~1288) gera exatamente um registro por empresa selecionada (wizardEmpresasSelecionadas.map(...)), independente de quantos empregados/sócios/rubricas existam — cada registro usa .find() (primeiro match) sobre os empregados/sócios/rubricas daquela empresa, não uma lista. Ou seja: "Consolidado" != "todos os empregados em um único doc"; é "1 doc por empresa, com dados de 1 registro representativo de cada fonte marcada". Isso é adequado para documentos que falam da empresa como entidade (ex.: um termo de responsabilidade da própria empresa), mas não serve para gerar, por exemplo, uma lista consolidada de todos os empregados em uma única tabela — não há suporte a isso no gerador hoje.
  • O editor de texto é contenteditable com document.execCommand (API deprecada, mas ainda funcional em todos os browsers evergreen) — não há sanitização de HTML na gravação do template; o que está no DOM do editor vai direto para a coluna, incluindo qualquer HTML colado pelo usuário.
  • Variáveis de planilha ({{excel.*}}) não têm uma lista fixa em VARS_DEF.excel.campos — esse array é preenchido em runtime a partir dos cabeçalhos da última planilha carregada (seja no modal do modelo, seja no wizard), então o painel de variáveis muda de conteúdo dependendo do que foi carregado por último na sessão.

Eventos

Stack e Estrutura de Arquivos

  • index.html — seção #eventos + modal (#modal-evento) com duas listas lado a lado (modelos disponíveis / modelos do evento) e reordenação por botões ↑/↓ (sem drag-and-drop).
  • app.js — CRUD em carregarEventos()/renderEventos()/salvarEvento()/deletarEvento(); seleção/ordem no modal em eventoModalSelecao (array de ids, a posição no array É a ordem) via adicionarModeloEvento()/removerModeloEvento()/moverModeloEvento().

Modelo de Dados

TabelaColunas-chaveObservações
gm_eventosid, nome, descricao, criado_porRLS igual a gm_modelos (SELECT aberto, escrita restrita a admin/criador).
gm_eventos_modelosevento_id FK, modelo_id FK, ordem INT, UNIQUE (evento_id, modelo_id)Só referencia — não duplica o template do modelo. RLS FOR ALL ... USING (true) (mais aberta que a das duas tabelas pai).
gm_geracoes.evento_idFK nullable para gm_eventosAdicionada depois de gm_geracoes já existir (ver schema-gerador-modelos-eventos.sql); permite filtrar histórico por evento sem alterar a granularidade de linha (ver Dashboard/Histórico).

Fluxo Principal

carregarEventos() busca gm_eventos e gm_eventos_modelos.select('evento_id, ordem, gm_modelos(*)') em paralelo via Promise.all — deliberadamente não depende do array global modelos (carregado por carregarModelos() ao mesmo tempo, sem ordem garantida entre as duas Promises na inicialização da página), montando modelosOrdenados a partir do próprio gm_modelos(*) embutido na consulta.

usarEvento(id) → _iniciarWizardComEvento(evento) trata o evento como um "modelo sintético": monta um objeto wizardModeloSelecionado fake com tipo: 'por_registro' fixo e fontes = união das fontes de todos os modelos do evento, mais 'empregados' forçado incondicionalmente (comentário no código: "eventos sempre geram por empregado"). O template desse objeto sintético é só a concatenação bruta dos templates dos modelos (usada apenas para calcularSequencia() detectar uso de {{excel.*}} — nunca é renderizado como texto final).

flowchart TD
    A[usarEvento id] --> B[_iniciarWizardComEvento]
    B --> C[Uniao das fontes de todos os modelos do evento + empregados forcado]
    C --> D[Monta modelo sintetico tipo por_registro]
    D --> E[calcularSequencia usando o sintetico]
    E --> F[Wizard segue fluxo normal de Empresas/Empregados/Socios/Rubricas/Planilha]
    F --> G[renderPreview e exportarPDF iteram evento.modelosOrdenados]
    G --> H[Um cabecalho + quebra de pagina por modelo, por registro]

Decisões de Design / Particularidades

  • Como o modelo sintético força tipo: 'por_registro', um Evento sempre gera um conjunto de documentos por empregado selecionado — mesmo que todos os modelos que o compõem sejam individualmente do tipo consolidado. O campo tipo de cada modelo individual só é relevante quando ele é gerado avulso (fora de um evento); dentro de um evento, é ignorado.
  • Excluir um evento (ON DELETE CASCADE em gm_eventos_modelos) não afeta gm_modelos — os modelos continuam existindo e utilizáveis avulsos.

Gerar / Wizard

Stack e Estrutura de Arquivos

  • index.html — seção #gerar: barra de passos (#wizard-steps-bar) + um <div class="wizard-panel"> por painel possível (WIZARD_PANELS_ORDER), todos no DOM o tempo todo, alternados por classe .active em mostrarPainel() — não é renderização condicional real, é show/hide via CSS.
  • app.js — núcleo do wizard: estado em variáveis globais soltas (wizardStep, wizardModeloSelecionado, wizardEmpresasSelecionadas, wizardRegistros, wizardEventoAtivo etc., ~15 variáveis no topo do arquivo) — não há um objeto de estado único nem um reducer, cada função lê/escreve as globais diretamente.

Modelo de Dados

Este painel não persiste dado próprio durante a navegação — só lê gm_modelos/gm_eventos e as tabelas RH (rh_empresas, rh_empregados, rh_socios, rh_rubricas). A única escrita fora do fechamento da geração é a logo da empresa (ver abaixo). Ao concluir (Exportar), grava em gm_geracoes — ver seção Dashboard/Histórico.

Tabela/ColunaPapel
rh_empresas.logo_base64TEXT nullable, adicionada por schema-gerador-modelos-logo-empresa.sql. Guarda a logo como data URI (data:image/png;base64,...) direto na linha da empresa — sem bucket de Storage. Compartilhada com outros módulos que leem rh_empresas (coluna puramente aditiva).

Fluxo Principal — Sequência dinâmica do wizard

calcularSequencia() (linha ~808) é a função central: recebe wizardModeloSelecionado.fontes e .template e devolve o array de passos ativos, a partir da ordem fixa WIZARD_PANELS_ORDER = ['modelo','empresas','empregados','socios','rubricas','planilha','exportar'].

  • usaExcel = fonte excel marcada OU o texto do template contém a substring {{excel. — ou seja, um modelo pode acabar exigindo o passo Planilha mesmo sem a fonte marcada explicitamente, só por ter uma variável {{excel.x}} colada no texto.
  • temFonteDB = alguma fonte entre empresas/empregados/socios/rubricas está marcada.
  • soExcel = usaExcel && !temFonteDB → modo "Excel puro": pula Empresas/Empregados/Sócios/Rubricas inteiramente.
  • Passo empresas é sempre o segundo passo quando não é modo Excel puro (não depende de a fonte empresas estar marcada — está implícito, porque toda geração parte de uma empresa).
flowchart TD
    A[calcularSequencia] --> B{fontes inclui excel OU template contem chave excel.}
    B -- nao --> C[usaExcel = false]
    B -- sim --> D[usaExcel = true]
    C --> E{alguma fonte DB marcada}
    D --> E
    E -- nao E usaExcel=true --> F[soExcel = true, modo Excel puro]
    E -- sim --> G[soExcel = false]
    F --> H[sequencia = modelo, planilha, exportar]
    G --> I[sequencia = modelo, empresas]
    I --> J{fontes inclui empregados}
    J -- sim --> K[push empregados]
    J -- nao --> L[skip]
    K --> M{fontes inclui socios}
    L --> M
    M -- sim --> N[push socios]
    M -- nao --> O[skip]
    N --> P{fontes inclui rubricas}
    O --> P
    P -- sim --> Q[push rubricas]
    P -- nao --> R[skip]
    Q --> S{usaExcel}
    R --> S
    S -- sim --> T[push planilha]
    S -- nao --> U[skip]
    T --> V[push exportar]
    U --> V
    H --> W[sequencia final]
    V --> W

wizardAvançar() reexecuta validações por painel corrente antes de avançar (ex.: exige ao menos 1 empresa marcada antes de liberar o passo seguinte) e, ao chegar em empresas, dispara carregarDadosDasEmpresas() (busca paralela de rh_empregados/rh_socios/rh_rubricas filtrados pelas empresas escolhidas, com todos os registros pré-selecionados por padrão). Ao chegar em exportar, chama construirRegistros() — se o wizard estiver em modo Excel puro e nenhuma coluna de empresa tiver sido detectada/escolhida, intercepta o avanço com abrirModalNomeEmpresaExcel() antes de montar os registros.

Fluxo Principal — Construção dos registros (construirRegistros)

flowchart TD
    A[construirRegistros] --> B{soExcel}
    B -- sim --> C[1 registro por linha da planilha, colunas viram excel.coluna]
    B -- nao --> D{modelo.tipo}
    D -- por_registro --> E{fonte empregados marcada E ha empregados selecionados}
    E -- sim --> F[1 registro por empregado selecionado]
    E -- nao --> G[1 registro por empresa selecionada]
    D -- consolidado --> H[1 registro por empresa selecionada, sempre]
    F --> I[buildVarMap cruza empresa/empregado/socio/rubrica/linha excel por indice]
    G --> I
    H --> I
    C --> J[wizardRegistros pronto]

O cruzamento empresa↔empregado usa codigo_empresa normalizado com .trim() dos dois lados antes de comparar (protege contra espaço acidental num dos dois cadastros); quando não encontra a empresa, loga console.warn e segue com objeto vazio {} em vez de lançar erro — o documento sai com os campos {{empresa.*}} em branco, silenciosamente, sem alertar o usuário na UI.

Fluxo Principal — Exportação PDF (impressão do navegador)

exportarPDF() agrupa wizardRegistros por empresa (_agruparRegistrosPorEmpresa, chave empresa.codigo_empresa com fallback pro nome) e, para cada grupo, monta o HTML das páginas (_montarPaginasPDF) e chama _abrirJanelaImpressao() — que faz window.open('', '_blank'), escreve o HTML completo via document.write e agenda window.print() num setTimeout escalonado (300ms + 700ms por grupo adicional, para não empilhar vários diálogos de impressão simultâneos quando há N empresas). Não há geração real de arquivo PDF no cliente — o "Salvar PDF" citado na UI depende inteiramente de o usuário escolher "Salvar como PDF" na caixa de impressão do navegador; se o navegador bloquear o pop-up (comum quando há múltiplas empresas abrindo várias janelas de uma vez), o código detecta (window.open retorna null) e avisa via toast, mas não tem fallback automático.

As duas bibliotecas de geração de PDF client-side (jsPDF, html2canvas) carregadas no index.html não são referenciadas em nenhuma função do app.js — parecem ter sido incluídas para uma abordagem alternativa (renderizar como imagem/canvas e gerar PDF binário de verdade) que nunca chegou a ser implementada, ou foi removida sem tirar o <script>. Ao dar manutenção nessa área, não assumir que essas libs fazem algo — confirmar com grep antes de mexer.

Fluxo Principal — Exportação Excel

exportarExcel() usa XLSX.utils.json_to_sheet sobre os próprios wizardRegistros (todas as chaves do varMap como colunas) mais uma coluna adicional documento_gerado = substituirVars(modelo.template, varMap, false) — o HTML renderizado do documento inteiro, cru, dentro da célula. Diferente do PDF, não há separação por empresa: todos os registros saem juntos numa única planilha/aba (nome da aba truncado em 31 caracteres, limite do formato XLSX).

Decisões de Design / Particularidades

  • Cabeçalho dos documentos (_gerarCabecalhoModelo) é gerado dinamicamente em runtime a partir de wizardCabecalho (completo/neutro/nenhum) + logo resolvida por _logoEmpresaDe(varMap) — não fica embutido no template do modelo (decisão histórica: os 9 modelos de Admissão tinham cabeçalho estático embutido até schema-gerador-modelos-remove-header-embutido.sql, migrado justamente para poder variar por empresa/registro e respeitar a escolha do wizard).
  • _logoEmpresaDe() resolve a logo por codigo_empresa quando disponível, com fallback por nome_empresa — necessário porque no modo Excel puro o registro pode não ter empresa.codigo_empresa (só o nome, se a coluna foi detectada).
  • "Ajustar para caber em 1 página" (wizardCaberUmaPagina) não corta conteúdo: mede scrollHeight de cada .pdf-fit-inner contra a altura útil de uma A4 (273mm em px) dentro da própria janela de impressão (script injetado via document.write) e aplica transform: scale() só quando estoura — nunca amplia quem já cabe.
  • Descartar um registro na pré-visualização (descartarRegistroPreview) faz wizardRegistros.splice() direto — é destrutivo dentro da sessão do wizard; navegar de volta para um passo anterior e avançar de novo reconstrói wizardRegistros do zero via construirRegistros(), perdendo o descarte.
  • No modo Excel puro, a detecção de coluna de empresa (_detectarColunaEmpresa) casa por nome de cabeçalho normalizado contra uma lista fixa de candidatos ("empresa", "cliente", "razão social", "nome fantasia" etc.) — é heurística de nome de coluna, não inspeciona o conteúdo das células.

Dashboard e Histórico

Stack e Estrutura de Arquivos

  • index.html — seção #dashboard (cards de estatística + duas listas "top 5") e seção #historico (tabela das últimas 100 gerações).
  • app.js — carregarDashboard() e carregarHistorico(), ambas fazem leitura direta de gm_geracoes sem view/RPC intermediária.

Modelo de Dados

TabelaColunas-chaveObservações
gm_geracoesid, modelo_id FK (ON DELETE CASCADE), modelo_nome (snapshot de texto — sobrevive à exclusão do modelo), empresas_ids (TEXT[] de codigo_empresa), total_registros, cabecalho_usado, criado_por, evento_id FK nullableRLS FOR ALL ... USING (true) para autenticado — sem restrição por criador (diferente de gm_modelos/gm_eventos). Só metadados: não guarda o PDF/Excel gerado, nem o HTML final dos documentos.

Fluxo Principal

registrarGeracao() é chamada ao final tanto de exportarPDF() quanto de exportarExcel() — mesma função para os dois caminhos de exportação, sem coluna que diferencie "gerado como PDF" de "gerado como Excel" no histórico. Quando wizardEventoAtivo está setado, insere uma linha por modelo do evento (evento.modelosOrdenados.map(...), todas com o mesmo total_registros/empresas_ids/evento_id) em vez de uma linha única para o evento — permite contar individualmente quantos de cada documento foram emitidos, ao custo de total_registros ficar “duplicado” N vezes por geração de evento com N modelos (soma agregada no Dashboard super-contaria registros se alguém decidisse somar por evento sem agrupar).

flowchart TD
    A[exportarPDF ou exportarExcel concluido] --> B[registrarGeracao]
    B --> C{wizardEventoAtivo setado}
    C -- sim --> D[1 insert em gm_geracoes por modelo do evento, mesmo evento_id]
    C -- nao --> E[1 insert em gm_geracoes para o modelo unico]
    D --> F[Historico/Dashboard leem gm_geracoes direto]
    E --> F

Decisões de Design / Particularidades

  • "Gerações hoje" no Dashboard é calculado no cliente comparando new Date(g.created_at).toDateString() com new Date().toDateString() — usa o fuso horário do navegador de quem está olhando o dashboard, não um fuso fixo do servidor.
  • Sem paginação real no Histórico — a consulta já limita a leitura, mas não há botão "carregar mais"; qualquer geração além do corte simplesmente não aparece na tela.

Dívida Técnica / Pendências

  • Sem diferenciação de canal de exportação (PDF vs. Excel) no histórico — se for necessário no futuro, precisa de coluna nova em gm_geracoes e ajuste nos dois pontos de chamada de registrarGeracao().
  • jsPDF/html2canvas carregados sem uso: ou remover os <script> do index.html (peso morto no carregamento da página), ou decidir formalmente adotá-los para gerar PDF de verdade em vez de depender da caixa de impressão do navegador.
