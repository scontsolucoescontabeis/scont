O Gerenciador de Formulários vive em Projeto Gerenciador Formularios/. Stack: HTML + JS puro (sem framework/bundler), um cliente Supabase por arquivo (supabase.createClient(SUPABASE_URL, SUPABASE_KEY) a partir de ../supabase-config.js). Os três formulários públicos (formulario_registro.html, formulario_alteracao.html, formulario_empregado.html) rodam sem autenticação — o cliente Supabase deles usa { persistSession: false, autoRefreshToken: false } e grava sob as policies anon insert do schema. As telas de gestão (index.html, historico.html, documentos.html, leitor.html) exigem login via portal-auth-guard.js e reaproveitam o mesmo app.js monolítico (~2100 linhas) como script único — index.html e historico.html carregam o arquivo inteiro mesmo usando só uma fração das funções. PDFs de resumo usam jsPDF 2.5.1 via CDN, direto no navegador (sem servidor). Exportação Excel usa SheetJS (xlsx.full.min.js, só em index.html). Todo upload de documento vai para o bucket privado documentos do Storage.

Painel de Gestão de Formulários

Stack e Estrutura de Arquivos

  • index.html — hub principal: sidebar, filtros, grid de cards, 4 modais (Detalhes, Edição, Documentos, Consulta CNAE). Carrega utils.js, cnaes.js (lista estática de CNAEs, ~2400 linhas de dados) e app.js.
  • app.js — módulo único com toda a lógica de listagem, filtros, modais, edição, exclusão lógica, geração de PDF de alteração, exportação Excel, histórico e Realtime. Não é dividido por tela; tanto index.html quanto historico.html e o órfão detalhes.html importam o arquivo inteiro.
  • detalhes.html — página de detalhe standalone (parâmetro ?id=), não referenciada por nenhum link da UI (só citada em um comentário de app.js linha 329). Não carrega portal-auth-guard.js nem ../supabase-config.js — se acessada diretamente, initSupabase() falha por SUPABASE_URL indefinido e não há gate de autenticação. Considerar página morta/insegura (ver Dívida Técnica).
  • utils.js — grab-bag de helpers genéricos (validação de CPF/e-mail, formatação de telefone/CEP/moeda, debounce/throttle, export CSV/JSON, logger). Só usado por index.html/historico.html/detalhes.html; os três formulários públicos não o carregam e reimplementam suas próprias versões desses helpers inline.

Modelo de Dados

TabelaPapel
formularios1 linha por envio de Registro ou Alteração de Empresa. tipo_formulario CHECK (registro/alteracao). status CHECK (recebido/validado/rejeitado/excluido). Colunas de registro e de alteração convivem na mesma tabela (larga, ~30 colunas), sem normalização por tipo.
sociosN por formulario_id (FK CASCADE). acao_socio (inclusão/edição/exclusão) só é preenchido em Alteração. documento_url/documento_nome apontam pro Storage.
empregados1 linha por ficha de admissão. Mesmo enum de status de formularios. cpf tem constraint UNIQUE — um segundo envio com o mesmo CPF quebra no INSERT (sem tratamento de "já existe" na UI, ver Dívida Técnica).
dependentesN por empregado_id (FK CASCADE).
arquivosTabela de referência a arquivos no Storage — praticamente não usada na prática: só formulario_alteracao.html tenta gravar nela, e com nomes de coluna que não existem no schema (ver Dívida Técnica). Registro/Empregado nunca inserem aqui; a navegação de documentos (viewDocuments em app.js, leitor.html) lista o bucket diretamente por path, sem depender desta tabela.
historico_edicoesLog de auditoria append-only. registro_id sem FK (aponta pra formularios ou empregados conforme tabela). Alimentado só por saveChanges() (evento EVENTO_EDICAO) e deleteForm() (evento EVENTO_EXCLUSAO) em app.js — nenhuma outra rotina grava aqui.
formulario_rascunho_tempNão está em schema_formularios.sql — definida à parte em _sql/formulario_rascunho_temp.sql (raiz do portal). PK token (UUID), coluna dados JSONB com o form serializado. RLS: anon só acessa a linha cujo token bate com o header x-rascunho-token (via current_setting('request.headers')); authenticated tem acesso total (suporte/auditoria).

    B -- nao --> D[pula formularios]
    A --> E{Sub-permissao empregados?}

Filtro de sub-permissão é decidido no client: window.gfPermissions vem de usuario_ferramentas.permissoes (buscado no DOMContentLoaded de cada página), casando a linha de ferramentas cujo url_base contém "gerenciador". Sem essa permissão o card/menu some da UI, mas a policy RLS de formularios/empregados é authenticated USING (TRUE) — um usuário autenticado sem a sub-permissão ainda consegue ler tudo via API direta.

Fluxo de Exclusão (soft delete)

sequenceDiagram
    participant U as Usuario
    participant A as app.js deleteForm
    participant DB as Supabase
    U->>A: clique lixeira, confirm
    A->>DB: UPDATE formularios/empregados SET status=excluido
    A->>DB: INSERT historico_edicoes EVENTO_EXCLUSAO
    DB-->>A: ok
    A->>A: loadForms recarrega lista
    Note over A: card some porque filterForms
descarta status excluido sempre

Exclusão nunca é DELETE — é sempre UPDATE status='excluido'. Não existe botão de "desfazer" na UI; reverter exige alterar a linha direto no banco (a linha e os relacionamentos FK — sócios, dependentes — continuam intactos).

Decisões de Design / Particularidades

  • Editar reescreve só um subconjunto de campos por tipo (if document.getElementById(...) guarda cada atribuição) — se um campo não existir no DOM do modal de edição naquele momento, ele simplesmente não é atualizado, sem erro.
  • Ao salvar edição, o sistema sempre tenta gerar e enviar um novo PDF (gerarEEnviarPDFAlterado) mesclando os dados originais com os atualizados — isso roda mesmo que a edição seja só uma troca de status, sem alteração de dado nenhum.
  • Realtime (setupRealtimeSubscriptions) escuta formularios, empregados e socios com debounce de 600 ms e sempre recarrega a lista inteira (loadForms()) — não há patch incremental por linha.
  • loadForms() busca as duas tabelas inteiras sem paginação server-side; a filtragem (busca, status, tipo, exclusão) acontece toda no cliente sobre o array já carregado.

Dívida Técnica / Pendências

  • detalhes.html é código morto/órfão, sem link de entrada e sem os scripts necessários pra funcionar (ver Stack acima) — candidato a remoção.
  • A única gravação real em arquivos (dentro de formulario_alteracao.html, upload de documento) usa nomes de coluna (arquivo_nome, arquivo_tipo, arquivo_tamanho, arquivo_url, arquivo_caminho) que não existem no schema real (nome_arquivo, tipo_documento, etc.) e não informa formulario_id/empregado_id — o INSERT falha sempre, mas está dentro de um try/catch que só faz console.warn, então o formulário salva normalmente e ninguém percebe a falha silenciosa. A mesma rotina também chama getPublicUrl() num bucket privado (public: FALSE), então a URL retornada não é utilizável — nenhuma tela usa esse campo, então não há impacto funcional hoje, só ruído de log.
  • O comentário de estrutura de pastas no final de schema_formularios.sql ("Formularios/Registro/…", "Empregados/{cnpj_empresa}/…") está desatualizado — os caminhos reais gravados pelos três formulários e lidos por viewDocuments() em app.js são Registro/{empresa}/…, Alteracao/{empresa}/… e Novos-Empregados/{empresa}/{empregado}/… (sem o prefixo Formularios/).
  • empregados.cpf é UNIQUE sem verificação prévia na UI — um segundo formulário para o mesmo CPF derruba o INSERT com erro de constraint, exposto ao usuário final como mensagem genérica de erro.

Formulário de Registro de Empresa

Stack e Estrutura de Arquivos

  • formulario_registro.html (1197 linhas) — página autocontida: form, validação, geração de PDF (jsPDF) e submissão, tudo em <script> inline.
  • Scripts carregados: ../supabase-config.js, jsPDF 2.5.1, @supabase/supabase-js@2, notificar-formulario.js. Não carrega rascunho-temp.js — diferente de Alteração e Empregado, este formulário não tem autosave; fechar a aba antes do envio perde o preenchimento.

Modelo de Dados

Grava em formularios (tipo_formulario='registro') e, em seguida, em socios por formulario_id. Não grava em arquivos — cada upload vai só para o Storage, path Registro/{nome_empresa_sanitizado}/formulario/ (PDF-resumo) e Registro/{nome_empresa_sanitizado}/documento/ (documento de cada sócio).

Fluxo Principal

    participant C as Cliente
    participant F as formulario_registro.html
    participant PDF as jsPDF
    participant ST as Storage documentos
    participant DB as Supabase
    participant EF as Edge Function enviar-email
    C->>F: preenche form, LGPD, socios

soma participacao = 100 porcento

Decisões de Design / Particularidades

  • Validação client-side trava o envio se a soma das participações societárias não fechar 100% (tolerância de 0.01) — não há constraint equivalente no banco; um INSERT feito fora dessa tela (API direta) não é bloqueado.
  • O envio é protegido contra duplo-clique por uma flag isSubmitting em memória (não é um lock no banco) — só evita duplo submit na mesma aba/sessão.
  • Falha ao salvar sócios não desfaz o formulário já salvo: o try/catch em torno do bloco de sócios apenas alerta o usuário ("dados da empresa salvos, mas houve erro ao salvar sócios") — não há transação nem rollback.
  • E-mail de notificação vai para contato@scontdf.com.br (config registro em notificar-formulario.js), diferente do endereço usado por Registro de Empregado.

Formulário de Alteração de Empresa

Stack e Estrutura de Arquivos

  • formulario_alteracao.html (1666 linhas), mesmo padrão autocontido do Registro.
  • Carrega rascunho-temp.js além de notificar-formulario.js. Inicializa window.RascunhoTemp.init(form, modoUrl, opts) no DOMContentLoaded, onde modoUrl vem de ?modo= na URL (default 'alteracao') — esse parâmetro só rotula o rascunho salvo (campo tipo_formulario de formulario_rascunho_temp); o INSERT final em formularios sempre grava tipo_formulario: 'alteracao', então ?modo=registro nesta página não transforma o envio em um registro de verdade.

Modelo de Dados

Mesmas tabelas de destino do Registro (formularios/socios), usando as colunas alterar_*/*_novo/*_nova do schema para os blocos condicionais. Sócios afetados carregam acao_socio (inclusao/edicao/exclusao). Path de Storage: Alteracao/{empresa_sanitizada}/formulario|documento/.

Fluxo Principal — Rascunho Automático

sequenceDiagram
    participant C as Cliente
    participant F as formulario_alteracao.html
    participant R as RascunhoTemp
    participant DB as formulario_rascunho_temp
    C->>F: abre link, com ou sem token na URL
    F->>R: init form, tipo, supabaseUrl/Key
    R->>R: getOrCreateToken le ou gera UUID, grava na URL
    R->>DB: SELECT dados WHERE token = self
    alt rascunho existe
        DB-->>R: dados salvos
        R->>F: restoreForm preenche campos, mostra banner
    else sem rascunho
        DB-->>R: vazio
    end
    loop a cada input ou change no form
        F->>R: scheduleAutoSave debounce 2s
        R->>DB: UPSERT token, dados, tipo_formulario
    end
    C->>F: envia formulario com sucesso
    F->>R: deleteOnSubmit
    R->>DB: DELETE WHERE token = self

O header x-rascunho-token é setado uma vez na criação do cliente Supabase dedicado (makeSbClient) — a policy RLS de formulario_rascunho_temp compara esse header com a coluna token da própria linha, então o token da URL é, na prática, a única credencial que protege o rascunho de outra pessoa.

Decisões de Design / Particularidades

  • RascunhoTemp.init recebe customSerialize (inclui __sociosCount__ no JSON salvo) e onBeforeRestore (recria os cards de sócio extras antes de repovoar os campos) — sem isso a restauração perderia os sócios além do primeiro.
  • Restaurar um rascunho não reidrata uploads de arquivo (rascunho-temp.js ignora el.type === 'file' tanto ao salvar quanto ao restaurar) — documentos precisam ser reanexados mesmo com o resto do formulário recuperado.
  • Mesmo padrão de proteção contra duplo envio (isSubmitting) e mesmo comportamento best-effort do e-mail do Registro.
  • E-mail de notificação também vai para contato@scontdf.com.br (config alteracao), mesmo destinatário do Registro.

Formulário de Registro de Empregado

Stack e Estrutura de Arquivos

  • formulario_empregado.html (1769 linhas — o maior dos três), mesmo padrão autocontido.
  • Carrega rascunho-temp.js e notificar-formulario.js, igual à Alteração.

Modelo de Dados

Grava em empregados (cpf UNIQUE) e, se houver filhos, em dependentes por empregado_id. dias_trabalho é TEXT[] (checkboxes de dia da semana). Uploads usam FOLDER_PATH = 'Novos-Empregados', path Novos-Empregados/{empresa_sanitizada}/{empregado_sanitizado}/{categoria}/, com categorias Formulario (PDF-resumo), Documentos-de-Identificacao, Documentos-Familiares, Documentos-Medicos.

Decisões de Design / Particularidades

  • Cada campo de upload acumula arquivos entre seleções (uploadedDocuments[categoria] é um array que recebe novos itens a cada evento change, sem substituir os anteriores) — permite anexar em cliques separados e remover um item específico antes do envio.
  • E-mail de notificação vai para pessoal@scontdf.com.br (config empregado em notificar-formulario.js) — destinatário diferente dos formulários de empresa, que vão para contato@scontdf.com.br.
  • empregados.cpf UNIQUE é a única constraint de unicidade de negócio em todo o módulo; não há verificação equivalente de CNPJ duplicado em formularios.

Histórico de Edições

Stack e Estrutura de Arquivos

  • historico.html — tela simples (busca + filtro de data) que reaproveita loadHistory()/filterHistory() de app.js, carregando o módulo inteiro só para essas duas funções.

Modelo de Dados

Lê só historico_edicoes (SELECT * ORDER BY editado_em DESC, sem paginação). Sem UPDATE/DELETE em nenhuma tela — a policy RLS da tabela nem define essas operações (só SELECT e INSERT para authenticated), então o log é imutável também no nível de banco, não só na UI.

Só duas rotinas em todo o módulo escrevem nesta tabela: deleteForm() (evento EVENTO_EXCLUSAO) e saveChanges() (evento EVENTO_EDICAO), ambas em app.js. Os três formulários públicos nunca gravam histórico — só a criação inicial do registro, que não é logada aqui.

Central de Documentos e Arquivos do Servidor

Stack e Estrutura de Arquivos

  • documentos.html — hub estático de cards (CSS próprio inline, não usa styles.css) linkando para os 3 formulários, o Gerenciador e o Leitor. Sem lógica de dados própria além do auth guard e do mesmo cálculo de sub-permissões replicado de index.html (não é uma função compartilhada).
  • leitor.html (692 linhas) — navegador de arquivos standalone: HTML/CSS/JS tudo no próprio arquivo, sem depender de app.js/utils.js. Cliente Supabase próprio, só para Storage.

Modelo de Dados

Nenhuma tabela — opera 100% sobre o bucket documentos via storage.from('documentos').list(path), .upload(path, file) e .remove([path]). Navegação por pastas é resolvida client-side a partir do path corrente (breadcrumb), sem relação com tipo_formulario ou IDs de formularios/empregados — é um explorador de arquivos genérico sobre a raiz do bucket, não filtrado por formulário.

Fluxo Principal

Decisões de Design / Particularidades

  • Leitura/gestão de arquivos é totalmente desacoplada de qual formulário gerou o documento — útil para limpeza manual, mas também significa que apagar um arquivo aqui não atualiza nenhum registro em formularios/empregados/arquivos (que, como já visto, quase não é usada mesmo).
  • documentos.html duplica a lógica de sub-permissões (usuario_ferramentas → filtra cards) já presente em index.html — qualquer mudança nesse cálculo precisa ser replicada nos dois arquivos manualmente.
