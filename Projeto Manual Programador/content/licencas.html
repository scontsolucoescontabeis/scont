O Controle de Licenças vive em Projeto Licenças/ e é um único arquivo index.html (~3.900 linhas) com HTML + CSS + JS inline — sem build step, sem módulos, sem framework. Um <script> só no fim do arquivo concentra toda a lógica (dashboard, documentos, processos, relatórios, configurações). Stack: cliente Supabase (@supabase/supabase-js@2 via CDN) usando as credenciais globais do portal (../supabase-config.js, projeto dsdqwigopzrdmxtmhsez), autenticação via ../portal-auth-guard.js (PortalAuthGuard.init(1)), Chart.js 4.4.0 para o dashboard, SheetJS (xlsx@0.18.5) para importar planilha de licenças, jsPDF 2.5.1 + AutoTable 3.8.2 para exportar relatórios em PDF. Navegação é por seções (showSection('dashboard'|'documentos'|'processos'|'relatorios'|'config')) que só alternam classList — não é SPA com router, é tudo a mesma página. Há um segundo arquivo solto, alerts-mobile.html, uma versão mobile-only do painel de alertas, linkado a partir de Projeto Central Alertas/ (ver Dívida Técnica — aponta para um projeto Supabase diferente do resto do portal). O modelo de dados original tinha uma tabela própria empresas (schema v3, com campos de LGPD); a v4 repontou tudo para rh_empresas e a tela "Clientes" foi removida — public.empresas continua no banco, órfã, sem tela nenhuma que a leia.

Dashboard

Stack e Estrutura de Arquivos

  • Tudo dentro de Projeto Licenças/index.html: HTML da seção #dashboard perto do topo do <body>, funções loadDashboard(), loadDashboardTable() e loadAlerts() no script inline.
  • KPIs (kpiAtivos, kpiVencendo, kpiVencidos, kpiEmpresasAtivas) e o painel "Alertas Visuais" (alertsList) são recalculados no cliente a cada carga da seção — nenhuma dessas contagens é persistida.

Esse "Alertas Visuais" do dashboard é independente do alerta por e-mail (ver seção Configurações/Alertas). Ele não usa dedupe (ultimo_alerta_nivel) nem checa se o alerta já foi enviado — recalcula do zero a cada vez que a seção é aberta, mostrando os 10 documentos mais próximos do vencimento (vencidos incluídos). É puramente informativo dentro da tela.

Decisões de Design / Particularidades

  • KPIs de vencimento usam janela fixa de 30 dias hardcoded (in30Days), independente do dias_alerta configurável em Configurações — só o painel "Alertas Visuais" (loadAlerts) e o alerta por e-mail respeitam esse valor configurável.
  • setupRealtimeListeners() assina postgres_changes em licencas/alvaras — qualquer INSERT/UPDATE/DELETE de outro usuário recarrega o dashboard automaticamente, sem polling.

Licenças e Alvarás (Documentos)

Stack e Estrutura de Arquivos

  • Mesma tela index.html, seção #documentos. CRUD via modal genérico (#recordModal) reaproveitado tanto para licenças quanto alvarás — o parâmetro data-table ('licencas' ou 'alvaras') nos botões de ação decide qual tabela cada operação (viewRecord/editRecord/updateRecord/deleteRecord) atinge.
  • Seletor de empresa é um modal próprio (#empresaPickerModal, funções openEmpresaPicker/renderEmpresaPickerList) que busca em rh_empresas — não é mais um <select> de uma tabela empresas local.
  • Importação em massa de licenças via Excel: baixarModeloLicencas() gera o template, importarExcelLicencas(file) lê com SheetJS e showImportPreview() confere antes de gravar.

toggleCamposDocumento() só esconde/mostra campos e alterna o atributo required no HTML — o servidor não valida nada disso; um INSERT feito fora da tela (script, painel Supabase) pode gravar qualquer combinação. O literal 'PENDENTE' em numero para Emissão é uma convenção de string, não um enum nem um valor sentinela reconhecido em consultas — filtros/relatórios que agrupam por numero ou fazem parsing dele precisam saber tratar esse caso.

Ciclo de Vida de um Documento

stateDiagram-v2
    [*] --> EmEmissao: tipo_operacao emissao, sem data_validade
    [*] --> Ativa: tipo_operacao renovacao, validade alem de 30 dias
    EmEmissao --> Ativa: edicao manual grava numero e datas reais
    Ativa --> ProximoVencimento: validade a menos de 30 dias
    ProximoVencimento --> Vencida: validade ja passou
    Vencida --> Ativa: edicao com nova data_validade futura
    Ativa --> [*]: soft delete, ativo false
    Vencida --> [*]: soft delete, ativo false

Esse status (situacaoDocumento(): "Em emissão" / "Sem validade" / "Vencida" / "Próximo vencimento" / "Ativa") é sempre calculado no cliente a partir de tipo_operacao e data_validade — não existe coluna status em licencas/alvaras. Cada tela que precisa exibir o status (Documentos, Relatórios, dashboard) recalcula essa mesma lógica de forma independente; não há um único ponto de verdade compartilhado, então uma mudança na regra (ex.: mudar o limiar de 30 dias) tem que ser replicada em cada função que hoje reimplementa esse cálculo (situacaoDocumento, os vários loadReport*, o dashboard).

Decisões de Design / Particularidades

  • Empresa é opcional (empresa_id nullable) — um documento pode existir sem vínculo a nenhuma rh_empresas, identificado só pelo texto livre em estabelecimento.
  • tipoLicencaOptionsHtml() preserva o valor gravado no <select> mesmo se o tipo tiver sido desativado no catálogo depois (mostra como "Nome (inativo)") — evita trocar silenciosamente o dado de um documento existente ao só abrir o formulário de edição sem tocar nesse campo.
  • Alvará não tem tipo_operacao: o conceito Emissão/Renovação é exclusivo do fluxo de Licença.

Processos

Stack e Estrutura de Arquivos

  • Seção #processos do mesmo index.html. Um processo é sempre vinculado a um documento existente (licença ou alvará) — openNewProcesso() carrega as duas tabelas juntas (tipo_tabela: 'licencas'|'alvaras') para popular o seletor.

Modelo de Dados

TabelaPapel
processosdocumento_id + tipo_documento ('licencas'|'alvaras') — FK "polimórfica" sem constraint de banco (não há FOREIGN KEY de fato, é só uma referência lógica resolvida no cliente). status com CHECK no banco (aberto, em_analise, aprovado, rejeitado, concluido, cancelado) — esse é o único status "de verdade" (persistido) da ferramenta inteira, ao contrário do status de documento (sempre calculado).
andamento_processosLog append-only (Art. 46 LGPD nos comentários do schema) — RLS só concede SELECT e INSERT; sem policy de UPDATE/DELETE, logo esses comandos são bloqueados a nível de banco, não só de UI.

Fluxo Principal

sequenceDiagram
    participant U as Usuario
    participant UI as index.html
    participant DB as Supabase

    U->>UI: saveProcesso ou updateProcesso
    UI->>DB: INSERT/UPDATE em processos
    DB-->>UI: status atual
    alt status mudou (ou criacao)
        UI->>DB: INSERT em andamento_processos (status_anterior, status_novo)
    end
    UI->>UI: fetchProcessos + loadAllAndamentos

Em updateProcesso() o status_anterior é lido do banco (SELECT status ... single()) logo antes do UPDATE, comparado ao novo valor do formulário — só grava andamento se o status realmente mudou. Em saveProcesso() (criação) sempre grava um andamento inicial com status_anterior: null.

Decisões de Design / Particularidades

  • Se o INSERT em andamento_processos falhar, o erro só vai pro console (console.error) — o processo em si já foi salvo/atualizado com sucesso e a tela mostra "sucesso" do mesmo jeito. Ou seja, é possível ter uma mudança de status em processos sem o log correspondente em andamento_processos (falha silenciosa, não é transação atômica).
  • documento_id não tem FK de banco porque aponta ora para licencas.id ora para alvaras.id — a integridade referencial depende inteiramente do código do front-end.

Relatórios

Stack e Estrutura de Arquivos

Sete sub-relatórios, cada um com sua própria função loadReport*(): Saúde Geral, Vencimentos (configurável por dias), Por Tipo, Clientes com Documentos Vencidos, Temporal, Conformidade, Processos. Configurações / Alertas de Vencimento por E-mail

Stack e Estrutura de Arquivos

  • Seção #config em index.html — cadastro do catálogo tipos_licenca (carregarTiposLicenca/adicionarTipoLicenca/removerTipoLicenca) e o formulário de alerta (alertEnabled/alertDays/alertEmail, funções saveConfig()/loadConfig()).
  • Novo em 2026-08-10 — Edge Function agendada Projeto Portal Scont/supabase/functions/alerta-licencas-vencimento/index.ts, registrada via pg_cron em schema_licencas_alertas_cron.sql. Reusa a Edge Function compartilhada Projeto Portal Scont/supabase/functions/enviar-email/index.ts (mesma função usada por Diário Contábil e Certificado Digital), com o template novo tipo: 'alerta_licenca_vencimento' (bloco em torno da linha 319 de enviar-email/index.ts).
  • Antes dessa mudança a configuração de alerta ficava só em localStorage do navegador e não existia envio de e-mail nenhum — só o campo na tela. Isso significava que o alerta "funcionava" só enquanto a aba ficava aberta, sem persistência real nem notificação de verdade.

Modelo de Dados

Tabela / ColunaPapel
configuracoes_licencas (chave/valor)Substituiu o localStorage. Chaves usadas: alertas_ativado ('true'/'false' como texto), dias_alerta (inteiro como texto, default 30), emails_alerta (lista separada por vírgula, único campo — não há tabela de destinatários). Upsert por chave a partir da tela; lida tanto pela tela (loadConfig) quanto pela Edge Function agendada — é o ponto de verdade compartilhado entre navegador e job.

alvaras.ultimo_alerta_nivel / ultimo_alerta_emIdêntico, para a tabela de alvarás.

RLS de configuracoes_licencas: SELECT e ALL (via FOR ALL ... WITH CHECK(true)) para authenticated — qualquer usuário logado no portal pode alterar os destinatários do alerta e-mail, não só admin/Configurações.

Fluxo Principal — Job Diário de Alerta por E-mail

sequenceDiagram
    participant CRON as pg_cron
    participant FN as Edge Function alerta-licencas-vencimento
    participant DB as Postgres service_role
    participant MAIL as Edge Function enviar-email

    CRON->>FN: POST diario, 11:15 UTC (~08:15 Brasilia)
    FN->>DB: SELECT configuracoes_licencas
    alt alertas_ativado = false ou sem destinatarios
        FN-->>CRON: 200, processed 0 (motivo no corpo)
    else configurado
        FN->>DB: SELECT rh_empresas (id, nome_empresa)
        loop para licencas e alvaras
            FN->>DB: SELECT documentos ativos (deletado_em IS NULL)
            loop para cada documento
                FN->>FN: calcula dias restantes e nivel (proximo/vencido)
                alt nivel nulo ou igual ao ultimo_alerta_nivel
                    FN->>FN: pula (sem duplicar alerta)
                else nivel novo
                    loop para cada destinatario configurado
                        FN->>MAIL: POST tipo alerta_licenca_vencimento
                    end
                    FN->>DB: UPDATE ultimo_alerta_nivel/ultimo_alerta_em
                end
            end
        end
        FN-->>CRON: 200, processed/alerted/destinatarios
    end

O nível de alerta é binário e mais simples que o de Certificado Digital: só 'proximo' (dentro de dias_alerta) ou 'vencido' (dias < 0) — não há os 3 níveis intermediários (atencao/urgente/critico) que existem no alerta de certificado. Diferente de Certificado Digital, também não existe um evento "renovado, alerta encerrado" — quando um documento é renovado e sai da janela de alerta, ultimo_alerta_nivel simplesmente fica desatualizado (nível antigo) até o próximo ciclo em que ele voltar a entrar em alerta, quando o nível muda de novo e o e-mail dispara normalmente. Não é um bug ativo, só uma simplificação deliberada em relação ao padrão de Certificado Digital.

Decisões de Design / Particularidades

  • Cron agendado 15 minutos depois do job de Certificado Digital (11:15 UTC vs 11:00 UTC), deliberadamente, para não disparar os dois ao mesmo tempo.
  • A Edge Function roda com SUPABASE_SERVICE_ROLE_KEY — ignora RLS por completo; ela é quem faz o UPDATE de ultimo_alerta_nivel mesmo a policy de UPDATE de licencas/alvaras sendo aberta a qualquer authenticated de qualquer forma.
  • emails_alerta é uma única string com múltiplos e-mails separados por vírgula — sem validação de formato de e-mail nem de tabela normalizada de destinatários.
  • O toggle "Tipo de Operação" das licenças (Emissão vs Renovação) não interfere no alerta: um documento em modo Emissão não tem data_validade, então daysLeft() retorna null e nivelAlerta() nunca dispara pra ele — fica de fora do job até virar Renovação com data real.
