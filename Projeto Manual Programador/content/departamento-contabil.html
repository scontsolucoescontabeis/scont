A Central do Departamento Contábil vive em Projeto Onboarding Contabil/ (nome de pasta histórico — a ferramenta cresceu de um único onboarding de clientes novos para 4 sub-áreas). Stack: HTML + JS puro (sem framework/bundler), um módulo IIFE por tela, cliente Supabase próprio por arquivo (supabase.createClient(SUPABASE_URL, SUPABASE_KEY)), autenticação via portal-auth-guard.js compartilhado do portal. Sem build step — os arquivos são servidos como estão. PDFs usam jsPDF 2.5.1 + AutoTable 3.8.2 via CDN (cdnjs), mesma versão em todas as ferramentas do portal que geram PDF. As 4 sub-áreas (Onboarding, Mapeamento Estratégico, Diário Contábil, Configurações) são uma única linha em ferramentas (url_base = ./Projeto Onboarding Contabil/index.html) — o controle de quem edita o quê é 100% client-side, não RLS por linha (exceção: bancos/contato, ver abaixo).

Visão Geral e Escopo Compartilhado

Arquivos por sub-área

  • index.html — hub: 4 cards (Onboarding, Mapeamento Estratégico, Diário Contábil, Configurações), sem lógica própria além do auth guard e do filtro "Configurações some pra Prestador de Serviço".
  • onboarding.html + onboarding.js — levantamento de documentos de empresas ingressantes.
  • mapeamento.html + mapeamento.js — perfil operacional/fiscal por empresa.
  • diario.html + diario.js (arquivo central, ~1400 linhas) + diario-relatorios.js + diario-validacoes.js + diario-historico.js + contabil-diario-util.js (funções puras testadas, ex.: calcularTemposFechamento).
  • configuracoes.html + configuracoes.js — empresas com contábil, responsáveis, alertas por e-mail.
  • migrar-diario-excel.html + .js — importador único (já executado) do Excel legado de lançamentos.
  • test-contabil-diario-util.js / test-mapeamento-nivel-atencao.js — únicos testes automatizados do módulo (Node puro, sem framework — rodar com node test-*.js).

Escopo de acesso (client-side, não RLS)

PapelComo é identificadoO que muda
Adminauth.isAdmin (portal-auth-guard)Vê e edita tudo, em todas as empresas.
Equipe SCONTauth.userData.empresa (case-insensitive) igual a "scont soluções contábeis"Mesmos poderes de edição do admin dentro do módulo (não é is_admin() do banco).
Prestador de Serviçoauth.userData.empresa igual a "prestador de serviço"Só lê; só vê empresas onde está em contabil_empresas_responsaveis; tela Configurações some do hub.

Cada arquivo recalcula esse escopo na própria _resolverEscopoUsuario() — não existe um módulo de auth compartilhado entre as 4 sub-áreas além do portal-auth-guard.js genérico do portal. Ao adicionar uma tela nova, replicar essa função, não assumir que o escopo "vem de algum lugar global".

Divida técnica transversal

  • Gating de edição é só client-side na maior parte do módulo — um usuário técnico com a anon key consegue escrever direto via API em quase todas as tabelas contabil_* (RLS = TO authenticated USING (true)). As únicas exceções com RLS real são contabil_mapeamento_bancos e contabil_mapeamento_contatos (ver seção Mapeamento Estratégico).
  • Nenhuma das 4 sub-áreas usa um framework de componentes — toda tela é innerHTML de template string + querySelectorAll pra religar listeners a cada re-render. Funciona, mas qualquer refatoração pra um framework precisaria reescrever o módulo inteiro, não incrementalmente.

Onboarding

Modelo de dados

TabelaPapel
contabil_onboardings1 linha por processo de onboarding (empresa, CNPJ, regime, respostas às perguntas-gatilho em colunas booleanas, status).
contabil_onboarding_itensN linhas por onboarding — 1 por item do checklist. Coluna secao (A-G = checklist do cliente; H = validação interna) decide upload (A-G) vs. só status (H). Catálogo fixo de itens vem de window.CONTABIL_CATALOGO (script separado, não uma tabela) e é filtrado pelas respostas das perguntas-gatilho ao gerar o onboarding.

Fluxo de geração do checklist

flowchart TD
    A[Novo Onboarding] --> B{Empresa nova?}
    B -- Sim --> C[Cria linha em rh_empresas]
    B -- Não --> D[Seleciona empresa existente]
    C --> E[Responde perguntas-gatilho]
    D --> E
    E --> F[Filtra catalogo CONTABIL_CATALOGO pelas respostas]
    F --> G[Gera linhas em contabil_onboarding_itens]
    G --> H[Checklist A-G: cliente envia arquivo]
    G --> I[Secao H: equipe SCONT so muda status]
    H --> J{status = aprovado ou nao_aplicavel?}
    I --> J
    J -- todos sim --> K[Progresso = 100%]

Decisões de design

  • Upload vai para o bucket Storage compartilhado documentos (mesmo bucket usado pelo balancete do Diário Contábil), path onboarding-contabil/<codigo_empresa>/<secao>/<item>_<nome_arquivo>. Leitura via createSignedUrl (60s), não URL pública.
  • Progresso é sempre calculado no cliente (progressoDe()), nunca persistido — evita a classe de bug "coluna denormalizada dessincroniza" (ver achado documentado no Manual do Programador de Certificado Digital, mesma categoria de problema já corrigida lá).

Sincronização automática (Configurações → Mapeamento)

configuracoes.js sincroniza responsavel_execucao (de contabil_empresas_responsaveis) e regime_tributario (de rh_empresas.regime_enquadramento, normalizado por texto livre) pra todas as empresas ativas toda vez que a tela de Configurações carrega — sempre sobrescrevendo, mesmo que alguém tenha editado manualmente esses 2 campos direto no Mapeamento entre uma sincronização e outra.

Algoritmo — Sugestão de Nível de Atenção

Função pura em mapeamento-nivel-atencao.js (calcularNivelSugerido, com export duplo window.*/module.exports — por isso dá pra testar com Node puro em test-mapeamento-nivel-atencao.js):

se situacao_2025_status == 'critico' OU situacao_2026_status == 'critico': retorna 'critico' atraso = mesesEntre(ultimo_mes_fechado, hoje) - tolerancia(periodicidade) tolerancia: mensal=1, trimestral=3, anual=12 se atraso >= 3: 'critico' se atraso == 2: 'alto' se atraso == 1: 'medio' senao: 'baixo'

Uma edição manual do nível seta nivel_atencao_travado = true, que desliga o recálculo automático até algum campo-gatilho (situacao_*, ultimo_mes_fechado, periodicidade) ser alterado de novo — não existe UI de "destravar" direto, só editando o banco.

Decisões de design

  • Sem acesso direto pelo hub por um tempo (2026-07-31) — voltou a ter card no hub em 2026-08-10, a pedido do usuário. Continua também acessível por empresa dentro do Diário (mapeamento.html?empresa=X&origem=diario), os dois caminhos coexistem.
  • Relatório PDF (gerarRelatorioPDF) omite bancos e contato do PDF quando quem gera não pode editar — mesma regra client-side da tela, não é enforcement de verdade (a informação já não foi buscada do banco nesse caso, então nem tem o que vazar pro PDF por esse caminho específico).

Diário Contábil

Modelo de dados

TabelaPapel
contabil_diario_lancamentosSó-inclusão (sem UPDATE/DELETE na UI). Colunas: texto livre, assunto (TEXT livre, lista fixa ASSUNTOS_LANCAMENTO só no front, não é enum no banco), mes_referencia/ano_referencia opcionais, autor/timestamp automáticos de sessionStorage.userAuth.

contabil_diario_fechamentosAppend-only (nunca UPDATE) — 1 linha por evento (enviado/aprovado/rejeitado). Status atual do fechamento é sempre derivado do evento mais recente, nunca armazenado numa coluna própria. Colunas balancete_url/balancete_nome (2026-08-10) apontam pro bucket documentos, path diario-contabil-balancetes/<codigo>/<ano>-<mes>/..., RLS de leitura restrita (ver Segurança abaixo).
contabil_diario_auditoriaAppend-only — log de toda transição de status da grade e de documentação disponível. Alimenta a tela Histórico junto com os lançamentos.

Máquina de estados — Grade Mensal

stateDiagram-v2
    [*] --> nao_iniciado
    nao_iniciado --> em_andamento: clique simples
    em_andamento --> pendencia: popover, motivo obrigatorio
    em_andamento --> concluido: popover
    pendencia --> em_andamento: clique simples (resolve)
    concluido --> em_andamento: reabrir (confirm), so se fechamento != aprovado
    concluido --> [*]: fechamento aprovado (trava)

Máquina de estados — Fechamento/Validação

stateDiagram-v2
    [*] --> aberto
    aberto --> aguardando_validacao: Prestador encerra (evento "enviado")
    aberto --> aprovado: equipe SCONT encerra (pula direto, sem evento "enviado")
    aguardando_validacao --> aprovado: evento "aprovado"
    aguardando_validacao --> aberto: evento "rejeitado" (motivo obrigatorio)
    aprovado --> [*]

O status nunca é uma coluna — statusFechamentoDoMes() olha só o tipo_evento do registro mais recente em contabil_diario_fechamentos pra aquele (codigo_empresa, ano, mes). Balancete (PDF) é obrigatório em qualquer caminho que feche o mês; a diferenciação "Prestador vs. equipe SCONT" é decidida em podeValidar() no momento do clique, não guardada em lugar nenhum.

Segurança / RLS não-trivial

  • contabil_pode_ver_balancete(caminho) (SECURITY DEFINER, policy em storage.objects): is_admin() OU equipe SCONT OU responsável pela empresa (via contabil_empresas_responsaveis + storage.foldername(name)[2] pra extrair o código da empresa do path). A policy antiga de leitura geral do bucket documentos teve que ganhar um NOT (name LIKE 'diario-contabil-balancetes/%') — sem isso as duas policies permissivas se somariam por OR e a nova não teria efeito nenhum (pegadinha real de RLS com múltiplas policies permissivas no mesmo comando).

Alertas por e-mail

5 eventos (validação enviada, aprovado, rejeitado, pendência criada, pendência sanada), cada um com toggle global (não por empresa) em contabil_config_geral. Todos reusam a Edge Function compartilhada enviar-email (mesma função usada por Certificado Digital e Licenças, cada uma com seu próprio tipo de template dentro de montarHtml()).

Decisões de design

  • Sem botão "Salvar" — todo toggle (contábil sim/não, responsável, alerta) grava direto no banco ao clicar; falha reverte a UI e mostra toast de erro.
  • Importação de planilha casa colunas por nome normalizado (sem acento/espaço, lowercase) contra uma lista de aliases — não é posicional. Linha com código não encontrado na base é ignorada silenciosamente (mantém o que já estava configurado).
