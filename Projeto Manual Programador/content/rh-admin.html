A Administração RH vive em Projeto RH/admin.html (~840 linhas, 8 abas em uma única página) + Projeto RH/admin.js (~2785 linhas, todas as funções em escopo global — sem IIFE, sem módulos — ligadas via onclick="" inline no HTML). Sem build step, sem framework: cada aba é innerHTML de template string re-renderizado a cada filtro/paginação. Cliente Supabase próprio (supabase.createClient(SUPABASE_URL, SUPABASE_KEY) de ../supabase-config.js), autenticação via portal-auth-guard.js compartilhado do portal. Bibliotecas via CDN: SheetJS (xlsx.full.min.js 0.18.5) para leitura/escrita de Excel e PDF.js 3.11.174 para os dois importadores de PDF (férias e jornada). Os parsers de PDF (ferias-parser.js, jornada-parser.js) são módulos puros — sem DOM, sem Supabase, sem PDF.js — que rodam tanto como <script> global no navegador quanto via require() em Node, cobertos por test-ferias-parser.js/test-jornada-parser.js (só usados por esta ferramenta, não compartilhados com o restante do módulo RH). A ferramenta é o cadastro mestre de rh_empresas/rh_empregados/rh_socios/rh_rubricas que alimenta as demais telas do módulo RH (Controle de Frequência, Gerar Folhas de Ponto, Gerar Benefícios etc.).

Escopo de Acesso por Responsável

Fluxo Principal

Ao carregar a página, _resolverEscopoUsuario() lê sessionStorage.userAuth (preenchido pelo portal-auth-guard.js) e decide se o usuário atual enxerga todas as empresas ou só um subconjunto. O resultado fica em _empresasPermitidas (variável global do módulo: null = sem restrição).

flowchart TD
    A[DOMContentLoaded] --> B[_resolverEscopoUsuario]
    B --> C{auth.isAdmin?}
    C -- sim --> D[_empresasPermitidas = null, ve tudo]
    C -- nao --> E{empresa do usuario == prestador de servico?}
    E -- nao --> D
    E -- sim --> F[SELECT codigo_empresa FROM contabil_empresas_responsaveis WHERE usuario_id]
    F -- sucesso --> G[_empresasPermitidas = Set dos codigos retornados]
    F -- erro --> H[_empresasPermitidas = Set vazio, nao mostra nenhuma empresa]
    D --> I[carregarEmpresas/Empregados/Ferias/Jornada/Socios/Rubricas]
    G --> I
    H --> I

Cada tela filtra sua lista carregada pelo escopo com _filtrarPorEscopo(linhas) (filtro em memória, pós-fetch) — exceto Rubricas, que é paginada no servidor e usa _aplicarEscopoQuery(query) (.in('codigo_empresa', [...set])) para filtrar antes da paginação. Se o escopo falhar ao carregar (erro de rede), o fallback é não mostrar nenhuma empresa — mais seguro que vazar tudo, mas também significa que uma falha silenciosa da API deixa a tela vazia sem erro visível além do console.

Decisões de Design / Particularidades

  • O gating é 100% client-side: RLS de todas as tabelas rh_* usadas nesta ferramenta é TO authenticated USING (TRUE) (ver seção Modelo de Dados de cada aba) — um usuário autenticado com a anon key lê/escreve qualquer empresa via API direta, independente do papel. A tela apenas não mostra o que está fora do escopo.
  • A tabela que define o escopo (contabil_empresas_responsaveis) pertence ao módulo Departamento Contábil, não ao RH — admin.js lê essa tabela de fora do seu próprio domínio. Mudanças na tela Configurações do Departamento Contábil (ver Manual do Programador daquele módulo) afetam diretamente quem vê o quê aqui.
  • Distinção de papel usa auth.userData.empresa (case-insensitive) comparado a strings fixas ("prestador de serviço") — não há enum nem tabela de papéis; renomear essa empresa cadastrada no portal quebra o gating silenciosamente (todo mundo passa a cair no ramo "vê tudo").

Aba Empresas

Modelo de Dados

TabelaPapel
rh_empresas1 linha por empresa, codigo_empresa UNIQUE. Colunas base em Projeto RH/schema_rh.sql (id, codigo_empresa, nome_empresa); colunas de cadastro completo (cnpj, regime_enquadramento, inscricao_estadual, inscricao_municipal, municipio, status_situacao, data_cadastro, endereco, cep, cidade) vêm de _sql/rh_importacao_campos.sql — arquivo na raiz do portal, fora da pasta Projeto RH/. Colunas uf e email/email_responsavel em migrações à parte (schema_rh_empresas_uf.sql, schema_rh_empresas_email.sql, schema_rh_email_responsavel.sql). RLS: TO authenticated USING (TRUE) em todas.

Fluxo Principal — Importação (relatório do ERP)

A importação lê o relatório "Relação de Empresas" exportado diretamente do ERP fonte — não um modelo próprio da ferramenta (o botão "Modelo" foi removido quando o layout mudou para o do ERP). O parsing é posicional: 7 linhas de título/paginação ignoradas (range=7 no SheetJS), 32 colunas mapeadas por índice fixo (várias em branco — resíduo de células mescladas do relatório original), nome_empresa vindo da coluna Razão Social (índice 27) e não da coluna "Empresa" (índice 2, truncada em ~28% das linhas do arquivo de referência).

flowchart TD
    A[Arquivo .xlsx/.xls/.csv] --> B[lerPlanilha com range=7, 32 colunas posicionais fixas]
    B --> C[Filtra linhas sem codigo_empresa ou nome_empresa]
    C --> D{Tabela rh_empresas ja tem linhas?}
    D -- nao --> E[Importa direto, sem perguntar]
    D -- sim --> F[Modal Substituir vs Acrescentar]
    E --> G[Busca UF por CEP em lotes de 5, ViaCEP + fallback por faixa numerica]
    F --> G
    G --> H{Modo == acrescentar e UF nao resolvida?}
    H -- sim --> I[Nao sobrescreve UF ja salva]
    H -- nao --> J[upsert em rh_empresas onConflict codigo_empresa]
    I --> J

Como codigo_empresa é UNIQUE, "Substituir" e "Acrescentar" resultam na mesma linha final para Empresas — a única diferença real entre os dois modos aqui é o tratamento de UF quando a busca pelo CEP falha (comentário explícito no código: um DELETE antes do insert quebraria FKs lógicas de outras tabelas, ex. contabil_onboardings.codigo_empresa).

A busca de UF é dupla: tenta a API pública ViaCEP primeiro; se a rede falhar, cai em _FAIXAS_CEP_UF, uma tabela de faixas numéricas de CEP por estado embutida no próprio admin.js. O botão "Preencher UF pendentes" roda o mesmo mecanismo avulso, para empresas com CEP mas sem UF.

Decisões de Design / Particularidades

  • O campo "E-mail Responsável" é editado inline na própria tabela (onblur salva direto, sem botão Salvar) — mesmo padrão sem-botão-salvar visto em outras telas do portal.
  • O filtro de Status (Ativo/Inativo) compara por prefixo de string ("ativ"/"inativ", case-insensitive) para cobrir tanto "Ativo" quanto "Ativa" vindos do ERP, já que status_situacao é texto livre, não enum.

Aba Empregados

Modelo de Dados

TabelaPapel
rh_empregadosPK lógica (codigo_empresa, codigo_empregado) UNIQUE. ~100 colunas: dados contratuais, cargo/função, documentos (CPF/PIS/RG/CTPS/CNH/RNE/passaporte), dados pessoais, endereço, situação trabalhista, dados bancários, deficiência, 7 blocos de dependente (nome/nascimento/CPF/parentesco). Colunas além das 3 base vêm de _sql/rh_empregados_campos.sql (fora de Projeto RH/). Coluna jornada_id existe (FK para rh_jornadas, ver quadro abaixo) mas não é lida nem exibida nesta tela.

Fluxo Principal — Listagem e Filtros

Busca paginada em blocos de 1000 linhas (range() em loop) para superar o limite padrão do Supabase — a tabela pode ter mais de 14 mil linhas somando todas as empresas. A grade de colunas é configurável: _GRUPOS_CAMPOS define 9 grupos temáticos de colunas; o usuário marca/desmarca quais aparecem na tabela, no Excel exportado (exportarRelatorioEmpregados) e no PDF (gerarRelatorioPDFEmpregados, que abre uma janela nova com HTML próprio e chama window.print() — não usa jsPDF/AutoTable como o resto do portal).

Os filtros (empresa via checklist, nome/código, situação via checklist, tipo de empregado) são todos aplicados em memória sobre a lista já carregada — não há re-fetch por filtro.

Fluxo Principal — Importação (mapeamento por nome de coluna, não por posição)

Diferente da importação de Empresas (posicional), a de Empregados lê por nome do cabeçalho, porque o relatório fonte ("Todas as empresas / Apenas Ativos") repete a linha de cabeçalho a cada troca de empresa dentro do mesmo arquivo, e a ordem de algumas colunas (ex. Agência/Conta) varia entre empresas.

flowchart TD
    A[Le todas as linhas com header igual a 1, sem mapeamento fixo] --> B{Linha parece cabecalho?}
    B -- sim --> C[_construirMapaColunasEmpregados mapeia indice do arquivo para chave interna, por rotulo]
    C --> D[Atualiza mapaAtual e continua]
    B -- nao --> E{Existe mapaAtual?}
    E -- nao --> F[Ignora linha, anterior ao 1o cabecalho]
    E -- sim --> G[Aplica mapaAtual a linha, gera registro cru]
    D --> H[Proxima linha]
    F --> H
    G --> H
    H --> I[Filtra registros sem codigo_empresa/codigo_empregado/nome_empregado]
    I --> J[Converte datas Excel/BR para ISO, salario para numero]
    J --> K[Modal Substituir vs Acrescentar]
    K --> L[upsert em lotes de 200, onConflict codigo_empresa+codigo_empregado]

Rótulos duplicados no modelo canônico (ex. "Categoria" aparece tanto para categoria do empregado quanto para categoria da CNH) são resolvidos por ordem de aparição: a N-ésima ocorrência de um rótulo no arquivo mapeia para a N-ésima ocorrência do mesmo rótulo no array canônico — depende da ordem das colunas no arquivo fonte ser estável entre blocos de empresa.

Decisões de Design / Particularidades

  • No modo "Substituir", o DELETE é por codigo_empresa IN (...) — apaga todos os empregados das empresas presentes no arquivo antes de reinserir, não linha a linha.
  • O deletar de empregado individual (botão 🗑 na tabela) é hard delete direto em rh_empregados — sem soft delete, sem confirmação além do confirm() nativo do navegador.

Aba Informações de Férias

Modelo de Dados

TabelaPapel
rh_ferias_calculadasUpsert por (codigo_empresa, codigo_empregado, ferias_inicio) — histórico acumulado (múltiplos períodos por empregado convivem), não snapshot. Alimenta também o badge "Férias" no Controle de Frequência (index.html), fora desta ferramenta.

Fluxo Principal

Importa o PDF "Relação de Férias Calculadas" (todas as empresas) via PDF.js: extrai textContent por página, reconstrói linhas de texto agrupando itens por posição Y (_reconstruirLinhasPagina em ferias-parser.js, tolerância de 1.0 no eixo Y), depois interpreta essas linhas com regras específicas do layout do relatório fonte (_parsearLinhasFerias). Linhas não reconhecidas viram avisos exibidos ao usuário (não silenciosamente descartadas) via _renderizarResumoImportacaoFerias. Antes de salvar, o código consulta as chaves já existentes em rh_ferias_calculadas para contar "novos" vs. "atualizados" por empresa no resumo pós-importação — sem esse SELECT prévio a UI não saberia diferenciar.

Decisões de Design / Particularidades

  • Esta aba é somente leitura na UI — sem edição/exclusão manual de período, só reimportação do PDF (que faz upsert, nunca limpa o que já existia antes de uma nova importação).

Aba Jornada de Trabalho

Modelo de Dados

TabelaPapel
rh_jornada_trabalho1 linha por (codigo_empresa, codigo_empregado, dia_semana) UNIQUE — horário real de entrada/intervalo/saída por dia da semana em que o empregado trabalha, importado do PDF "Horário de Trabalho". Snapshot, não histórico: cada importação por PDF faz DELETE de toda a tabela antes de reinserir (comentário explícito no schema e no código: "reflete o estado atual da jornada de todos os empregados").

Não confundir com rh_jornadas (tabela criada em schema_rh_jornadas.sql, 05/08/2026): essa é a feature de múltiplas jornadas nomeadas por empresa (jornada diária + exceções de sexta/sábado), configurada na tela Configurações do Controle de Frequência (index.html / script.js — fora desta ferramenta) e associada a empregados via rh_empregados.jornada_id (NULL = usa a "Jornada Padrão" da empresa, guardada em rh_config_rubricas_txt). admin.js não lê nem escreve rh_jornadas em nenhum ponto — são dois conceitos de "jornada" com o mesmo nome de domínio e tabelas distintas, propositalmente separados desde a migração original (comentário no SQL: "conceito separado, não afetado por esta migração"). Quadro comparativo:

rh_jornada_trabalho (esta aba)rh_jornadas (Configurações do Controle de Frequência)
GranularidadePor empregado × dia da semanaPor empresa, nomeada (ex. "Turno Noturno"), associada N:1 a empregados
Origem do dadoImportação de PDF do sistema fonteCadastro manual na UI de Configurações
ConsumidorAdministração (esta tela) e Gerar Folhas de PontoCálculo de frequência/extras no Controle de Frequência e Gerar Benefícios
Comportamento em import/ediçãoSnapshot — substitui tudo a cada PDF importadoCadastro persistente, editado incrementalmente

Fluxo Principal — Importação e Edição Manual

O parser (jornada-parser.js) agrupa itens do PDF.js por linha (mesma técnica Y do parser de férias) e depois por coluna, usando faixas fixas de posição X (_COLS_JORNADA: codigo, nome, dia, entrada, intervalo, saida, observacao) — não por proximidade textual. Isso existe para resolver um caso real do PDF fonte: quando o nome do empregado é comprido, ele "gruda" sem espaço com a data de admissão da coluna vizinha (ex. "SANTOS14/07/2018"); agrupar por posição X evita que esse vazamento contamine as outras colunas — só a coluna nome precisa de limpeza (corta a partir da 1ª data encontrada).

flowchart TD
    A[PDF Horario de Trabalho] --> B[PDF.js extrai items com posicao X/Y por pagina]
    B --> C[Agrupa por linha, Y com tolerancia 1.0]
    C --> D[Classifica cada item por coluna, faixa fixa de X]
    D --> E[_parsearLinhasJornada monta registros codigo/nome/dia/horarios]
    E --> F[DELETE FROM rh_jornada_trabalho neq id impossivel, ou seja apaga tudo]
    F --> G[INSERT em lotes]
    G --> H[carregarJornadaInfo agrupa por empregado para exibicao]

A tela agrupa as 7 linhas (uma por dia) de um mesmo empregado em 1 linha de tabela (colunas Segunda…Domingo). A edição manual (modal "Editar Jornada") opera direto sobre rh_jornada_trabalho: desmarcar um dia faz DELETE da linha daquele dia; marcar/editar faz upsert por (codigo_empresa, codigo_empregado, dia_semana). Validações no salvamento: entrada e saída obrigatórias se o dia está marcado como trabalhado; entrada deve ser antes da saída; intervalo exige início E fim preenchidos, ou nenhum dos dois.

Decisões de Design / Particularidades

  • Uma nova importação de PDF apaga edições manuais feitas na tela desde a última importação — o snapshot é literal (delete-then-insert), sem merge.

Aba Sócios

Modelo de Dados

TabelaPapel
rh_sociosUNIQUE (codigo_empresa, nome_socio). Tabela e colunas base (nome, cpf, participação, cargo, data_entrada) criadas em _sql/rh_importacao_campos.sql; colunas adicionais (capital_social, email_empresa, data_atualizacao_quadro, data_saida, email_socio) em _sql/rh_socios_novos_campos.sql — ambos fora de Projeto RH/, junto com as colunas extras de rh_empresas (ver aba Empresas).

Fluxo Principal

Cadastro CRUD completo (form com editar/cancelar) além de importação em lote. A situação da empresa (Ativa/Inativa) exibida na linha do sócio é resolvida por lookup em _todasEmpresas (já carregada pela aba Empresas) — não é uma coluna de rh_socios, então a aba Sócios depende de Empresas já ter sido carregada no mesmo carregamento de página (ambas disparadas em paralelo no DOMContentLoaded, sem await entre elas — corrida benigna: se Sócios renderiza antes de Empresas terminar, o nome/CNPJ/situação aparecem como "—" até o próximo re-render).

A importação deduplica por (codigo_empresa, nome_socio) dentro do próprio arquivo antes de enviar ao banco — a última ocorrência de uma chave repetida prevalece, e o número de duplicatas descartadas é reportado ao usuário.

Decisões de Design / Particularidades

  • No modo "Substituir" o DELETE é por empresa inteira (mesma lógica de Empregados) — sócios que saíram e não estão mais no arquivo importado são apagados, não marcados como inativos.

Aba Rubricas

Modelo de Dados

TabelaPapel
rh_rubricasUNIQUE (codigo_empresa, codigo_rubrica). Colunas empresa (nome desnormalizado, gravado no momento do cadastro/import), descricao_rubrica, tipo (texto livre, sem enum) vêm de schema_rh_rubricas_v2.sql — a tabela original em schema_rh.sql só tinha evento/codigo_rubrica (mapeamento evento→rubrica para geração de TXT de folha, ver rh_config_rubricas_txt, tabela separada e não gerenciada por esta aba).

Fluxo Principal

Única aba com paginação real no servidor (select('*', {count:'exact'}).range()) em vez de carregar tudo e paginar em memória — decisão dimensionada para o volume de rubricas (uma empresa pode ter centenas). Filtros de empresa/texto/tipo são aplicados como cláusulas Supabase (.eq/.or ilike) antes da paginação, e passam por _aplicarEscopoQuery para respeitar o escopo do Prestador de Serviço (única aba, junto de Empresas, que aplica o escopo na query em vez de só filtrar em memória).

Import/export/cadastro manual convivem: o card "Rubricas" existe tanto na aba dedicada quanto na aba Importar Dados (mesmo handleImportarRubricas, dois <input type="file"> diferentes apontando para a mesma função — por isso a função atualiza dois elementos de status distintos, statusImportarRubricas e statusImportarRubricasTab).

Decisões de Design / Particularidades

  • No cadastro manual (não na importação), o codigo_rubrica é upsert por (codigo_empresa, codigo_rubrica) — editar uma rubrica existente pelo formulário sobrescreve a linha em vez de duplicar; na importação em modo "Substituir" é DELETE+INSERT por empresa, igual às demais entidades.
