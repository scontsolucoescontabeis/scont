O CRM WhatsApp vive em Projeto CRM/ e é a única ferramenta do portal construída como SPA React — todo o resto do Portal Scont é HTML/JS vanilla sem build step. Stack real: React 18 + React Router 6 (HashRouter, base /scont/crm/) + Vite 6 + Supabase JS v2, com Tailwind 3 configurado no projeto mas praticamente não usado (a UI é quase 100% style={{...}} inline; a única tela com className Tailwind é ConexaoWhatsAppPage.jsx). recharts é usado só em Métricas; xlsx só em Contatos (importação) e Tarefas (exportação). npm run build gera dist/ e o Vite copia o resultado para ../crm — ou seja, o build final vira a pasta crm/ na raiz do portal, que é o que está de fato linkado em ferramentas. O app roteado real fica em src/pages/ + src/components/ + src/hooks/ + src/services/crm.service.js, todos importados a partir de src/App.jsx. Existe uma árvore paralela src/modules/crm/ e src/demo/DemoApp.jsx que não é importada por App.jsx em nenhum ponto — código morto, não documentado aqui como funcionalidade ativa (ver Dívida Técnica em cada seção para os pontos onde isso importa de verdade). src/contexts/AuthContext.jsx e CRMContext.jsx também estão vazios — apesar do nome da pasta, não há Context API real; sessão e perfil vivem em useState dentro de App.jsx e descem por props. Autenticação é Supabase Auth (e-mail/senha) mais SSO via hash — o portal abre o CRM em nova aba passando access_token/refresh_token no hash da URL, que App.jsx captura e grava com supabase.auth.setSession. Canais de WhatsApp: dois canais mutuamente exclusivos controlados pela tabela singleton whatsapp_config — API Oficial (Meta Cloud API, webhook com validação HMAC) e QR Code (Evolution API/Baileys auto-hospedada, webhook autenticado só por token de query string). O envio (send-message) decide o canal em tempo de execução lendo whatsapp_config.canal_ativo; o recebimento depende de qual webhook está de fato configurado do lado de fora (Meta Business Manager ou instância Evolution).

Envio — agente digita e clica em enviar:

flowchart TD
    A[Agente digita e envia] --> B[useWhatsApp.enviarMensagem]
    B --> C[insert direto em mensagens via client Supabase]
    C --> D[update conversas atualizado_em e status]
    D --> E[chama Edge Function send-message]
    E --> F{Chamada teve sucesso?}
    F -- Sim --> G[Mensagem sai de fato pelo WhatsApp]
    F -- Falhou ou Edge Function indisponivel --> H[erro é engolido em try catch]

    I --> J[Nenhum aviso é mostrado ao agente]

Decisões de Design / Particularidades

  • O envio de mensagem é otimista e fire-and-forget: useWhatsApp.enviarMensagem grava direto em mensagens pelo client (RLS aberta) e só depois chama supabase.functions.invoke('send-message', ...) dentro de um try/catch que silencia qualquer erro (_tentarEnviarWhatsApp). Se a Edge Function falhar, não estiver deployada, ou o canal não estiver configurado, a mensagem fica visível no CRM como enviada mas nunca sai pelo WhatsApp — sem qualquer sinalização para o agente.
  • As Edge Functions encerrar-conversa e transferir-conversa (que enviam a mensagem de encerramento e disparam o CSAT via Meta API, ou registram a transferência) não são chamadas por nenhum código da árvore ativa. O hook realmente montado (src/hooks/useWhatsApp.js) reimplementa a mesma lógica só com updates diretos no banco (conversas/mensagens/transferencias), sem invocar essas duas funções. Confirmado por grep: as únicas referências a encerrar-conversa/transferir-conversa fora da própria pasta supabase/functions estão em src/modules/crm/hooks/useWhatsApp.js — árvore morta. Na prática, hoje, clicar em Encerrar no ChatPanel real não envia a mensagem de despedida nem a pesquisa CSAT pelo WhatsApp.
  • Mídia recebida é baixada da Graph API pelo próprio whatsapp-webhook e reenviada para o bucket privado crm-midia (path <conversaId>/<timestamp>.<ext>); falha de upload é silenciosa e não bloqueia o processamento do webhook. Leitura no front via createSignedUrl(mediaPath, 3600) — URL expira em 1h.
  • Polling de 20s em useConversas coexiste com o Realtime como fallback, caso um evento seja perdido.
  • Tailwind está no package.json/tailwind.config.js/index.css mas a interface inteira é construída com objetos style inline — a única exceção encontrada no código ativo é className="animate-spin" em ConexaoWhatsAppPage.jsx. Ao editar qualquer tela, manter o padrão inline em vez de migrar parcialmente para classes Tailwind.

Máquina de estados executada em processarMensagemBot a cada mensagem recebida:

Decisões de Design / Particularidades

  • dentroDoHorario() converte o horário atual manualmente para America/Sao_Paulo via toLocaleString porque a Edge Function roda em UTC no runtime Deno — não usa nenhuma lib de timezone.
  • enviarMenu tenta lista interativa da Meta primeiro (máx. 10 linhas — acima disso trunca em 9 + opção "Outros"); se a chamada falhar, cai para um menu numerado em texto puro. Dívida Técnica / Pendências

  • O estado AGUARD_AVAL (avaliação CSAT) só é criado pela Edge Function encerrar-conversa — e essa função não é chamada por nenhum código da árvore ativa do front (ver seção Atendimento). Na prática, hoje, nenhuma sessão chega a AGUARD_AVAL em produção: a aba "Avaliações" do ChatbotPage e a tabela chatbot_avaliacoes existem e funcionam tecnicamente, mas não recebem dados pelo fluxo real de encerramento usado pelos agentes.

Conexão WhatsApp

Stack e Estrutura de Arquivos

  • src/pages/ConexaoWhatsAppPage.jsx + src/hooks/useWhatsAppConexao.js.
  • supabase/functions/evolution-connect/index.ts — só ADMIN; reconecta uma instância Evolution existente ou cria uma nova já com o webhook configurado, extrai o QR code em base64 da resposta.
  • supabase/functions/evolution-webhook/index.ts — recebe eventos da Evolution API (MESSAGES_UPSERT, CONNECTION_UPDATE, QRCODE_UPDATED), autenticado só por token na query string (?token=EVOLUTION_WEBHOOK_TOKEN), sem HMAC.

Modelo de Dados

TabelaPapel / RLS
whatsapp_configSingleton (id=1, CHECK(id=1)). canal_ativo enum QR_CODE/API_OFICIAL, status_conexao enum DESCONECTADO/CONECTANDO/CONECTADO, qrcode_base64. RLS de leitura e escrita restrita a EXISTS (SELECT 1 FROM usuarios WHERE id = auth.uid() AND role = 'ADMIN').

Fluxo Principal

sequenceDiagram

    participant EC as evolution-connect
    participant Evo as Evolution API
    participant EW as evolution-webhook
    participant DB as whatsapp_config

    EC->>DB: status_conexao = CONECTANDO

Decisões de Design / Particularidades

  • Trocar de canal (trocarCanal) é um simples UPDATE em canal_ativo, sem validar se o canal escolhido está de fato pronto — é possível trocar para API Oficial sem as variáveis WHATSAPP_* configuradas e só descobrir no próximo envio, quando send-message falhar.
  • RLS de whatsapp_config checa usuarios.role = 'ADMIN' diretamente na tabela, diferente do padrão usado no resto do CRM (get_user_role(), que também reconhece is_admin=true do portal). Um admin do portal cujo usuarios.role não esteja explicitamente setado como 'ADMIN' pode ver a página no app (que usa get_meu_perfil_crm()) mas ter a query de leitura/escrita em whatsapp_config bloqueada pela RLS. O mesmo padrão de checagem direta em role aparece em sla_config (ver seção SLA) e em mensagens_prontas.
  • evolution-webhook não valida assinatura, só um token estático de query string — mais fraco que a validação HMAC do whatsapp-webhook da Meta.

SLA de Atendimento

Stack e Estrutura de Arquivos

  • src/pages/SLAConfigPage.jsx — tela de configuração por departamento (tempo máximo/avisos) e multiplicadores por classificação, dois botões de salvar independentes.
  • src/hooks/useSLA.js — exporta a função pura calcSLAStatus(conversa, slaConfig, classificacaoConfig) e o hook useSLA que a reaplica a cada 1s via setInterval.
  • Consumido em CRMPage.jsx (alimenta PainelSLA) e em ConversaList.jsx/ConversaCard.jsx (badge de contagem regressiva por conversa na lista).

Modelo de Dados

TabelaPapel / RLS
sla_configdepartamento PK (TEXT, não enum), tempo_maximo_min, threshold_aviso_min, threshold_critico_min, ativo. RLS de escrita: EXISTS (... WHERE id=auth.uid() AND role='ADMIN') — mesmo padrão direto-na-coluna de whatsapp_config.
classificacao_sla_configclassificacao PK (OURO/PRATA/BRONZE/SEM_CLASSIFICACAO), multiplicador NUMERIC > 0. RLS de UPDATE aberta para qualquer authenticated (não checa role) — inconsistente com a escrita de sla_config, que exige ADMIN.

Fluxo Principal

Lógica confirmada em calcSLAStatus — só é avaliada para conversas com status = 'ABERTA' e sem nenhuma mensagem de origem AGENTE ainda:

maxMs = tempo_maximo_min * multiplicador_da_classificacao * 60000 avisoMs = threshold_aviso_min * 60000 criticoMs = threshold_critico_min * 60000 elapsed = agora - aberto_em restante = maxMs - elapsed restante <= 0 -> VENCIDO restante <= criticoMs -> CRITICO restante <= avisoMs -> AVISO caso contrario -> OK, sem alerta

Só o tempo máximo é multiplicado pela classificação do cliente — os thresholds de aviso e crítico continuam em minutos absolutos, iguais para qualquer tier.

flowchart TD
    A[Conversa esta ABERTA?] -->|Nao| Z[sla_status = OK, sem alerta]
    A -->|Sim| B[Ja existe mensagem de origem AGENTE?]
    B -->|Sim| Z
    B -->|Nao| C[Busca sla_config do departamento]
    C --> D{ativo = true?}
    D -->|Nao| Z
    D -->|Sim| E[calcula maxMs com multiplicador do tier]
    E --> F[restante = maxMs menos tempo decorrido]
    F --> G{restante menor ou igual a zero}
    G -->|Sim| H[VENCIDO]
    G -->|Nao| I{restante menor ou igual ao critico}
    I -->|Sim| J[CRITICO, pisca]
    I -->|Nao| K{restante menor ou igual ao aviso}
    K -->|Sim| L[AVISO]
    K -->|Nao| M[OK]

Decisões de Design / Particularidades

  • SLA é 100% calculado no client, recalculado a cada 1s; não existe coluna persistida nem cron/Edge Function dedicada — sair e voltar da tela recalcula do zero a partir de aberto_em.
  • calcSLAStatus depende de conversa.mensagens vir embutido no select de useConversas (join sem limite) só para checar se existe alguma mensagem de agente. Isso significa que o select de conversas traz todas as mensagens de cada conversa (mesmo as antigas e fora do chat aberto) — sem paginação nem limite, o que pode pesar em conversas longas.
  • O relógio do SLA para na primeira mensagem de AGENTE ou quando o agente clica em Assumir (que muda o status para EM_ATENDIMENTO, tirando a conversa do universo status='ABERTA' filtrado por calcSLAStatus) — os dois caminhos levam ao mesmo resultado por rotas diferentes do código.

Decisões de Design / Particularidades

  • Portal admin (is_admin=true) sempre vira ADMIN do CRM em todos os departamentos automaticamente — a tela só permite editar departamentos/perfil de quem não é admin do portal (o botão de editar fica desabilitado/redundante para eles).
  • O fallback de configurarAcessoCRM/revogarAcessoCRM para a migration 005 ainda não ter rodado detecta a ausência da coluna checando se a mensagem de erro do Postgres contém a substring 'departamentos' — se o texto do erro do Supabase mudar de formato, esse fallback deixa de funcionar silenciosamente.

Painel de Métricas

Stack e Estrutura de Arquivos

  • src/pages/MetricasPage.jsx — 4 abas internas (Geral/Equipe/Tempo/Qualidade) mais LiveStrip (faixa "ao vivo" com Realtime), tudo no mesmo arquivo. Único ponto do CRM que usa recharts (BarChart, PieChart).
  • src/services/crm.service.js — calcPeriodo, buscarMetricasVivo, buscarMetricasGeral, buscarMetricasEquipe, buscarMetricasTempo, buscarMetricasQualidade.

Modelo de Dados

Não existe tabela ou view própria de métricas. Tudo é calculado sob demanda no client a partir de conversas, mensagens e transferencias — sem RPC agregada nem materialized view no Postgres.

Fluxo Principal

sequenceDiagram
    participant DB as conversas
    participant RT as Supabase Realtime
    participant Live as LiveStrip
    participant Tab as Aba selecionada

    RT->>Live: postgres_changes qualquer evento em conversas
    Live->>DB: 4 selects count exact head aberta/em_atendimento/aguardando/agentes
    DB-->>Live: contadores atualizados
    Note over Tab: troca de aba ou periodo
    Tab->>DB: select bruto do periodo, sem RPC agregada
    DB-->>Tab: linhas de conversas ou mensagens ou transferencias
    Tab->>Tab: agregacao feita em JavaScript no client

Decisões de Design / Particularidades

  • TMA na aba Tempo mede o tempo total de vida da conversa (encerrado_em - aberto_em) — é uma métrica diferente do SLA (que mede só até a primeira resposta do agente). As duas convivem em telas separadas com definições de tempo distintas.
  • "Agentes ativos" na faixa ao vivo é o tamanho do Set de agente_id distintos entre conversas EM_ATENDIMENTO — um agente com 5 conversas conta 1x; um agente só com conversas AGUARDANDO/ABERTA (que ainda não assumiu nada) não conta.
  • Cada evento Realtime em conversas (qualquer INSERT/UPDATE/DELETE) dispara 4 novas queries count na faixa ao vivo — sem debounce.
  • Delta percentual vs. período anterior é calculado no client comparando com uma segunda query do mesmo tamanho de intervalo, imediatamente anterior (calcPeriodo calcula inicioPrev/fimPrev).

Dívida Técnica / Pendências

  • Sem cache nem agregação no banco — em volumes grandes de conversas, buscarMetricasGeral/buscarMetricasEquipe/buscarMetricasQualidade trazem linha a linha (status/departamento/datas) de todas as conversas do período para agregar em JavaScript no navegador, a cada troca de aba ou período.

Simulador WhatsApp

Stack e Estrutura de Arquivos

  • Projeto CRM/public/docs/simulador-whatsapp.html (com uma segunda cópia em docs/simulador-whatsapp.html, fora de public/ — não é idêntica: caminhos relativos de supabase-config.js/portal-auth-guard.js têm profundidade diferente entre as duas, e uma chama PortalAuthGuard.init(2) enquanto a outra chama init(3)) — HTML/JS vanilla, sem Vite/React, arquitetonicamente igual ao resto do portal e não à árvore React do CRM. Carrega Supabase JS via CDN UMD (unpkg.com/@supabase/supabase-js@2), autentica com o mesmo portal-auth-guard.js e supabase-config.js usados pelas ferramentas vanilla do portal. É registrado no portal como ferramenta separada, mas fica fisicamente dentro da árvore do CRM; public/docs/ é copiado literalmente pelo Vite para dist/docs/, que vira crm/docs/ no build final.
  • supabase/functions/dev-message/index.ts — Edge Function que fabrica um payload no formato do webhook da Meta e o repassa para whatsapp-webhook.

Modelo de Dados

Sem tabela dedicada. A lista de "telefones simulados" fica só em localStorage do navegador (chaves wpp_sim_clientes e wpp_sim_config) — não é sincronizada entre dispositivos ou usuários. As conversas/mensagens simuladas gravam nas mesmas tabelas contatos/conversas/mensagens do tráfego real.

Fluxo Principal

sequenceDiagram
    participant Sim as simulador-whatsapp.html
    participant DM as dev-message
    participant WH as whatsapp-webhook
    participant Bot as chatbot-processor
    participant RT as Supabase Realtime

    Sim->>DM: POST phone, name, message, bypass_token
    DM->>WH: POST payload no formato Meta, header X-Dev-Bypass-Token
    WH->>WH: bypass_token valido, pula validacao HMAC
    WH->>Bot: processarMensagemBot, mesmo fluxo de producao
    Bot-->>WH: grava respostas em mensagens
    WH-->>DM: retorna conversa_id, contato_id, protocolo
    DM->>DM: busca historico completo com service role
    DM-->>Sim: retorna mensagens ja carregadas
    RT-->>Sim: subscricao propria por conversa_id, novas mensagens em tempo real

Decisões de Design / Particularidades

  • O simulador chama dev-message usando o access_token da própria sessão autenticada do usuário do portal (com fallback para a anon key) no header Authorization — mas quem efetivamente autoriza o bypass da assinatura HMAC no whatsapp-webhook é o DEV_BYPASS_TOKEN enviado em X-Dev-Bypass-Token, configurado nas variáveis de ambiente da Edge Function e digitado manualmente na tela do simulador (⚙ Configuração).
  • Migration 011_dev_simulator.sql abre SELECT sem nenhuma restrição em mensagens, conversas e usuarios, com um comentário explícito "usar apenas em ambiente de dev" — mas a policy fica ativa em qualquer ambiente onde a migration tenha rodado, sem flag para desligá-la em produção.

Dívida Técnica / Pendências

  • Existem duas cópias do arquivo (public/docs/simulador-whatsapp.html e docs/simulador-whatsapp.html) e elas já divergem hoje — não são só paths relativos diferentes, o argumento passado a PortalAuthGuard.init() também é diferente entre as duas (2 vs. 3). Como é public/docs/ que o Vite copia para o build publicado, essa é a versão que roda de verdade; docs/ (fora de public/) parece ser uma cópia esquecida ou desatualizada — checar as duas ao editar, ou apagar a que não é servida, para não divergirem mais.
