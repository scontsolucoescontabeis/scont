Duas ferramentas relacionadas do módulo RH, cada uma documentada em sua própria <section>: o Conversor de Folha de Ponto (Projeto RH/conversor.html + conversor.js) transforma o PDF exportado pelo Sólides ou pelo SmartPonto no Excel que o Controle de Frequência importa; o Renomeador de Arquivos (Projeto RH/renomeador.html + renomeador.js) aplica regras de nomenclatura cadastradas em rh_regras_renomeacao e grava os arquivos renomeados em dois destinos. O Renomeador também existe como app desktop em Projeto Renomeador Electron/ (Electron — main.js/preload.js/renderer.js, empacotado com electron-builder), com a mesma lógica de regras portada para lá; esse app não é detalhado aqui.

Conversor de Folha de Ponto

Stack e Estrutura de Arquivos

  • conversor.html — wizard de 4 etapas (Upload → Configuração → Colaboradores → Dados e Geração), sidebar do módulo RH, sem framework, CSS embutido inline no próprio HTML além de styles.css compartilhado.
  • conversor.js — estado único em state (empresa, competência, colaboradores extraídos do PDF, vínculos, colaboradores confirmados), controla a navegação entre etapas e chama os parsers.
  • folha-ponto-solides-parser.js e folha-ponto-smartponto-parser.js — módulos puros (sem DOM, sem Supabase, sem PDF.js), carregados como <script> globais e também via require() nos testes Node. Cada PDF é roteado para um dos dois conforme o formato detectado.
  • Funções do parser SmartPonto usam sufixo Smart (_parsearPaginaColaboradorSmart, _melhorMatchEmpregadoSmart etc.) — comentário no próprio arquivo explica que é para não colidir em silêncio com as funções de mesmo nome do parser do Sólides, já que os dois scripts vivem no mesmo escopo global da página.
  • Bibliotecas via CDN: pdf.js 3.11.174 (leitura do PDF no browser, getTextContent() por página) e SheetJS xlsx 0.18.5 (geração do Excel final, XLSX.writeFile — download direto, sem passar pelo servidor).
  • Cliente Supabase próprio (supabase.createClient(SUPABASE_URL, SUPABASE_KEY)), autenticação via portal-auth-guard.js compartilhado do portal.
  • Testes: test-folha-ponto-solides-parser.js e test-folha-ponto-smartponto-parser.js — Node puro sem framework, rodar com node test-folha-ponto-solides-parser.js / node test-folha-ponto-smartponto-parser.js.
  • Fora de escopo desta ferramenta: folha-ponto-calculo.js está na mesma pasta e tem nome parecido, mas é usado pela tela "Folha de Ponto" (index.html do módulo RH, geração do horário previsto a partir de rh_jornada_trabalho), não pelo Conversor — fácil de confundir escopo por causa do prefixo comum folha-ponto-*.

Modelo de Dados

rh_empresasSó leitura — codigo_empresa, nome_empresa, carregada inteira na Etapa 1/2 para a busca/autocomplete de empresa.
rh_empregadosSó leitura — codigo_empregado, nome_empregado, situacao, filtrada por codigo_empresa da empresa selecionada e por situacao != 'Demitido'; usada como universo de destino do vínculo fuzzy na Etapa 3.

O Conversor não grava nada no Supabase. O resultado (Excel) é gerado e baixado inteiramente no cliente via XLSX.writeFile; a persistência acontece depois, manualmente, quando esse Excel é importado no Controle de Frequência.

Decisões de Design / Particularidades

  • Parser Sólides — segmentação por dia: _dividirBlocosDia usa como âncora o padrão regex DD/MM + dia da semana por extenso (ex.: 05/06 quinta-feira) para cortar o texto corrido da página em um bloco por dia; dentro do bloco, tudo depois de Total: é descartado antes de seguir para o parsing de horários.
  • Parser Sólides — horários vs. status: _parsearCorpoDia divide o bloco do dia por |. Sem |, o bloco inteiro é um status sem batida (falta/abono/feriado). Com |, os segmentos antes do último viram pares Entrada/Saída na ordem em que aparecem, e o segmento depois do último | (totais do dia) é descartado. Se um segmento sai com 1 ou 3+ horários (contaminação por quebra de linha do PDF original), o parser interrompe a leitura daquele dia em vez de gravar um horário errado — o comentário no código chama isso de proteção deliberada, deixando a correção para a revisão manual da Etapa 4.
  • Parser SmartPonto — layout tabular denso, sem separador |: o export do SmartPonto não tem colunas delimitadas por caractere; é texto denso com colunas de largura fixa (JORNADAS REALIZADAS | NORMAL | EXTRA | LIMITE 1/2/3 | BANCO HR. | HORÁRIOS PREVISTOS) onde um corte único por posição X não é confiável. A extração usa "âncora mais próxima": localiza o X do rótulo NORMAL (fronteira boundaryX) e os X dos rótulos ENT./SAÍ. à esquerda dela (âncoras de jornada); cada token de uma linha de dia entra na zona "jornada real" só se estiver mais perto de alguma âncora de jornada do que da fronteira NORMAL — senão é descartado (pertence a Normal/Extra/Limites/Banco de Horas/Horários Previstos).
  • Detecção de formato: teste simples de substring (_pareceSolides / _pareceSmartPonto) sobre o texto concatenado de todas as páginas, decidido uma única vez antes de rodar o parser — não há mistura de formatos dentro do mesmo PDF/leva.
  • Preenchimento de dias faltantes: quando a competência é detectada, cada parser gera antes um esqueleto com todos os dias do mês (_gerarDiasDoMes / _gerarDiasDoMesSmart) e depois mescla os dias efetivamente extraídos do PDF por sobre esse esqueleto (_mesclarDias / _mesclarDiasSmart) — garante 1 linha por dia do mês no Excel final mesmo se o PDF pular ou omitir algum dia.
  • Vínculo fuzzy (Etapa 3): _melhorMatchEmpregado(Smart) normaliza nome (remove acento, lowercase, colapsa espaços) e prioriza igualdade exata; na ausência dela, usa o primeiro includes() bidirecional encontrado — não há score/ranking, é "primeiro que bater" na ordem em que rh_empregados foi carregado (ordenado por nome).
  • Terceiro turno (colunas Entrada 3/Saída 3) só aparece na tabela de revisão e no Excel se algum dia de algum colaborador do arquivo realmente tiver entrada3/saida3 preenchidos — calculado em prepararEtapa4 via state.maxPeriodos.
  • Aba "Ocorrências" do Excel gerado é só informativa (consolidado de status por colaborador/data); o importador do Controle de Frequência não a reconhece como aba de colaborador — o aviso de "aba não encontrada" nesse ponto é esperado.

Dívida Técnica / Pendências

  • O parser SmartPonto depende de encontrar os literais exatos NORMAL, ENT. e SAÍ. como âncoras de coluna (_acharBoundaryXSmart, _acharJornadaAnchorsSmart). Se o export do SmartPonto mudar esses rótulos, a ordem das colunas ou o idioma, o parser não lança exceção — simplesmente não encontra âncoras e extrai zero dias, silenciosamente.
  • Nome do arquivo folha-ponto-calculo.js convive na mesma pasta com os dois parsers (folha-ponto-solides-parser.js, folha-ponto-smartponto-parser.js) mas pertence a outra tela — risco real de um programador futuro assumir que os três formam um conjunto e mexer no lugar errado.

Renomeador de Arquivos

Stack e Estrutura de Arquivos

  • renomeador.html — página standalone com CSS embutido próprio (variáveis --primary-color etc. redefinidas localmente, não reaproveita styles.css do módulo RH nem a sidebar padrão).
  • renomeador.js — estado em variáveis de módulo soltas (regrasCadastradas, empresasCadastradas, mapeamentosCadastrados, arquivosCarregados, arquivosAnalisados), sem objeto state único como no Conversor.
  • Cliente Supabase próprio (supabase.createClient(SUPABASE_URL, SUPABASE_KEY)), autenticação via portal-auth-guard.js.
  • Sem bibliotecas de PDF/Excel — grava direto em disco via File System Access API nativa do navegador (window.showDirectoryPicker, getFileHandle/createWritable), sem gerar arquivo intermediário.
  • CRUD de regras e de mapeamentos de nome fica em Projeto RH/admin.js (funções carregarRegras/salvarRegra/deletarRegra e carregarMapeamentos/salvarMapeamento/deletarMapeamento, dentro de admin.html) — renomeador.js só lê essas tabelas, nunca escreve nelas.
  • Projeto Renomeador Electron/ — app desktop separado (main.js, preload.js, renderer.js, empacotado em dist/SCONT Renomeador Setup 1.0.0.exe) com a mesma lógica de casamento de regras portada para lá; grava direto no sistema de arquivos do Windows sem depender da File System Access API do browser. Repositório de código próprio, não compartilha arquivo JS com o Renomeador web.

Modelo de Dados

O Renomeador não grava nada em nenhuma tabela — só lê as três acima. A "gravação" da ferramenta é sempre em disco local, via File System Access API, nunca no Supabase.

Decisões de Design / Particularidades

  • Motor de regex (criarRegexDoPadrao): escapa os caracteres especiais de regex do padrao_de e só depois substitui os placeholders por grupos nomeados:
{CODIGO_EMPRESA} → (?<codigo>\d+) {NOME_ARQUIVO} → (?<nome>.+?) {MM} → (?<mes>\d{2}) {AAAA} → (?<ano>\d{4}) {IGNORAR} → .*? (trecho descartado, sem grupo nomeado) Regex final: ^<padrao_de convertido>$ com flag "i" (case-insensitive) testada contra o nome do arquivo SEM extensao.
  • Ordem de casamento: o array de regras vem de select('*') sem order() — a ordem depende do que o Postgres/PostgREST devolver (na prática, próxima da ordem física/de inserção, não garantida por contrato). A primeira regra que casar é aplicada e o loop para (break); não existe priorização por especificidade nem detecção de regras ambíguas/conflitantes.
  • Extensão original é sempre preservada à parte — cortada do nome antes do match e reanexada ao final do novo nome montado, nunca passa pelo regex nem pelo template de saída.
  • Segunda fase de placeholders (montagem do novo nome e do caminho Dinâmico) resolve {CODIGO_EMPRESA} e {NOME_ARQUIVO} a partir dos grupos capturados no match, {NOME_EMPRESA} via rh_empresas, {NOME_DOCUMENTO} via rh_mapeamento_nomes (fallback para o nome de arquivo cru se não houver mapeamento cadastrado), e {MM}/{AAAA} vêm da Competência digitada no Passo 1 — não do {MM}/{AAAA} eventualmente capturado do próprio nome do arquivo original.
  • Separador de caminho: o caminho Dinâmico é normalizado para / internamente (barras trocadas e barras nas pontas removidas) para servir de lista de segmentos de pasta na gravação via File System Access API, e só é convertido de volta para \ na exibição da tabela de prévia — tratamento manual de string, sem lib de path.
  • Gravação em disco depende de window.showDirectoryPicker — só Chrome/Edge 86+; se ausente, a ferramenta mostra aviso e não tenta nenhum fallback (nem download, nem ZIP) nesse fluxo web.
  • Discrepância entre UI e código: o texto fixo "Como funciona" em renomeador.html ainda diz que o sistema "gerará um arquivo .ZIP contendo duas pastas"; isso está desatualizado — salvarNosDestinos() não gera ZIP algum, grava diretamente nas duas pastas escolhidas pelo usuário via File System Access API. Quem for dar manutenção não deve se basear nesse texto para entender o mecanismo real.

Dívida Técnica / Pendências

  • RLS de rh_regras_renomeacao e rh_mapeamento_nomes é totalmente aberta para qualquer usuário authenticated (USING (TRUE) tanto para leitura quanto para escrita) — mesmo padrão observado em outros módulos do portal; o controle de quem pode editar regras é só "quem tem o link de admin.html", não enforcement de banco.
  • Sem detecção de regras conflitantes/ambíguas: duas regras cujo padrao_de uma seja mais genérica que a outra, cadastradas na ordem errada, fazem a mais específica nunca ser alcançada (a primeira que casar vence, ver "Ordem de casamento" acima) — sem aviso na tela de admin nem no Renomeador.
  • Texto "Como funciona" desatualizado (menção a ZIP) mencionado acima — deveria ser corrigido para refletir a gravação direta via File System Access API, evita confundir tanto usuário quanto programador futuro lendo o HTML.
