A Triagem de Atendimentos vive em Projeto Triagem/: dois arquivos HTML+JS puro, sem framework/bundler, cliente Supabase próprio por arquivo (supabase.createClient(SUPABASE_URL, SUPABASE_KEY)) e autenticação via portal-auth-guard.js compartilhado do Portal. A origem dos dados é inteiramente externa ao Portal: a captura das conversas do Gestta Messenger e a classificação por departamento/categoria/prioridade acontecem em scripts soltos fora deste repositório de fato (mesmo estando versionados dentro da pasta), rodando na máquina do usuário ou num agendamento do Windows Task Scheduler — o Portal só entra em cena depois que a planilha triagem_atendimento.xlsx já está pronta. Não existe backend próprio: todo o parsing do .xlsx é client-side, com SheetJS (xlsx.full.min.js 0.18.5, via cdnjs) rodando no navegador em upload.html, e a mesma lógica de parsing é reimplementada em Python (openpyxl) em upload_triagem.py para o caminho agendado. Cada upload substitui 100% dos dados anteriores (delete-all seguido de insert) — não existe histórico de uploads dentro das tabelas.

Upload da Planilha

Stack e Estrutura de Arquivos

  • upload.html — tela do Portal. HTML+JS puro, protegida por portal-auth-guard.js. Lê o .xlsx inteiramente no navegador com XLSX.read(buf, { type: 'array' }) (SheetJS) e envia o resultado direto pro Supabase com o cliente JS autenticado da sessão do Portal.
  • script captura messenger.txt — não é tela do Portal. Script de console: o usuário cola no F12 do navegador aberto na página do Gestta Messenger. Faz scroll/clique programático nas abas "Pendentes" e "Em Atendimento", extrai bolhas de mensagem por seletor CSS e acumula tudo em gestta_historico.txt local (últimos 3 dias, arquivo único reescrito a cada ciclo). Roda só enquanto a aba do navegador estiver aberta com o script colado.
  • gestta_chat_extractor.py + agendar_gestta.bat — caminho alternativo de captura, via Selenium, agendado no Task Scheduler do Windows a cada 5 minutos (schtasks /sc MINUTE /mo 5). Gera Desktop\atendimentos\atendimentos.txt, incremental. Coexiste com o script de console acima; o repositório não deixa claro qual dos dois é o caminho realmente em uso hoje — os dois produzem formatos de texto parecidos mas não idênticos.
  • Nenhum script deste repositório classifica as conversas capturadas por departamento/categoria/prioridade nem monta as 3 abas (Triagem / Resumo / Triagem Completa) da planilha final. Essa etapa — a que de fato produz triagem_atendimento.xlsx a partir do texto bruto — não tem código correspondente aqui; é um processo manual ou uma ferramenta externa não documentada neste projeto.
  • upload_triagem.py + agendar_upload_triagem.bat — segundo caminho de upload, paralelo ao upload.html. Agendado a cada 30 minutos (schtasks /sc MINUTE /mo 30), lê a planilha em Desktop\captura_messenger\Triagem de Atendimentos - Gestta\triagem_atendimento.xlsx (mesmo caminho exibido na UI de upload.html) com openpyxl e grava direto na API REST do Supabase via requests, sem passar pelo Portal nem pelo auth guard.
  • Parsing duplicado: parseTriagem/parseResumo/parseTriagemCompleta existem em JS dentro de upload.html e são reescritas quase linha a linha em Python (parse_triagem/parse_resumo/parse_triagem_completa) em upload_triagem.py — duas implementações independentes da mesma regra de parsing, sem teste automatizado comparando as duas.

Decisões de Design / Particularidades

  • Substituição total a cada envio: as 3 tabelas são limpas (.delete().gte('id', 0) / .eq('id', 1)) antes de qualquer insert, tanto em upload.html quanto em upload_triagem.py. Não há soft-delete nem tabela de histórico de uploads — o upload anterior simplesmente deixa de existir.
  • Tamanho de lote do insert de triagem_conversas difere entre as duas implementações: 50 registros por lote em upload.html, 200 em upload_triagem.py — sem justificativa documentada para a diferença.
  • O vínculo entre uma demanda e sua conversa não é gravado em nenhuma tabela — é recalculado a cada carregamento da tela (findConv() em index.html), comparando o nome do cliente normalizado contra contact_key.
  • A RLS de escrita das 3 tabelas exige auth.role() = 'authenticated'. upload.html herda isso da sessão do Portal (o cliente Supabase-js roda autenticado depois do portal-auth-guard.js). Já upload_triagem.py chama a API REST só com a chave anon (o próprio JWT dessa chave tem "role": "anon", decodificável em texto simples no início do arquivo) e nunca abre uma sessão de fato — pelas regras de RLS definidas em create_triagem_tables.sql, essas chamadas deveriam ser rejeitadas. Vale confirmar no ambiente real se o agendamento de 30 minutos está de fato gravando dado ou falhando silenciosamente (o script só loga erro localmente via logging, sem alertar ninguém no Portal).

Dívida Técnica / Pendências

  • Duas implementações paralelas do parser da planilha (JS em upload.html, Python em upload_triagem.py) e dois scripts paralelos de captura (console vs. Selenium) — nenhuma das duplicações tem teste automatizado garantindo que ficam sincronizadas, e não está documentado se ambos os pares seguem em uso ou se um deles está obsoleto.
  • Risco de RLS descrito acima em upload_triagem.py (chave anon sem sessão vs. policy exigindo authenticated) — não verificado em produção nesta sessão, só via leitura de código.

Dashboard

Stack e Estrutura de Arquivos

  • index.html — arquivo único (~1060 linhas) com sidebar, header, as duas "páginas" (Dashboard e Triagem) e o modal de conversa, tudo no mesmo documento. Não é SPA com router: switchPage() apenas alterna display: none/'' entre #pageDashboard e #pageTriagem.
  • Autenticação via portal-auth-guard.js (PortalAuthGuard.init(1)), cliente Supabase criado só depois do guard liberar.
  • Sem gráficos de biblioteca externa — as barras de "Por Departamento" e "Por Prioridade" são <div>s com width calculada em JS, sem Chart.js nem SVG.

Decisões de Design / Particularidades

  • hasData é true se triagemRows.length > 0 ou Object.keys(resumoData.byDept).length > 0 — cobre o caso raro de a aba Resumo trazer totais agregados mesmo com a aba Triagem vazia.
  • Departamentos e prioridades não são uma lista fixa no código: cards, cores de gráfico e opções do filtro de departamento são derivados dinamicamente de resumoData.byDept/byPrio e de triagemRows. Cores têm um mapa fixo (deptColors, prioColors) com fallback (#8B3A3A) para valores não mapeados.
  • Auto-refresh é polling burro via setInterval(REFRESH_MS = 30_000), recarregando as 3 tabelas inteiras a cada ciclo — não há Supabase Realtime nem atualização incremental, e o timer não é limpo ao trocar de página dentro da mesma aba (só é recriado se loadFromSupabase() for chamado de novo).

Dívida Técnica / Pendências

  • triagem_dashboard.html (707 linhas, na raiz de Projeto Triagem/) é um protótipo anterior — inclui supabase-config.js e xlsx.full.min.js no <head>, mas em nenhum ponto do arquivo chama createClient ou faz qualquer parsing de planilha. Não é referenciado por nenhum link, redirecionamento ou script de outro arquivo do Portal (confirmado por busca em todo o repositório) — parece ter sido superado pela divisão atual em index.html + upload.html e nunca removido.

Demandas Triadas

Stack e Estrutura de Arquivos

  • Mesmo arquivo index.html, seção #pageTriagem: barra de filtros (cliente/departamento/prioridade), tabela e modal de conversa. Sem componente separado — tudo é innerHTML de template string mais querySelectorAll pra religar os onclick a cada renderTable().
  • Filtros são 100% client-side sobre o array triagemRows já carregado em memória — applyFilters() não refaz consulta ao Supabase, só alterna a classe hidden nas linhas já renderizadas do DOM.

findConv() (idêntica em espírito a normName do lado Python) para na primeira regra que encontrar uma correspondência — não soma pontuação nem escolhe a "melhor" entre múltiplas candidatas; a primeira chave do objeto conversations que bater no laço for...of vence.

Decisões de Design / Particularidades

  • Tela é somente leitura — não existe nenhuma chamada de update/insert nesta seção do arquivo; qualquer correção de dado exige novo upload da planilha.
  • Contagem de mensagens exibida (💬 N msg) filtra fora as mensagens type === 'system' — o aviso "(sem mensagens no período)" não conta como mensagem real.
  • Modal de conversa é montado inteiramente no cliente a partir do array já carregado — abrir o modal não dispara nova consulta ao Supabase.

Dívida Técnica / Pendências

  • Colunas dados e dom de triagem_demandas são gravadas em todo upload mas não têm nenhum consumidor na UI — candidatas a remoção do schema ou a alguma tela futura que ainda não existe; hoje são peso morto.
  • O algoritmo de correspondência de nomes (findConv/_norm_name) não é coberto por nenhum teste automatizado — qualquer ajuste na heurística de prefixo/sufixo/duas-primeiras-palavras precisa ser validado manualmente contra a planilha real.
