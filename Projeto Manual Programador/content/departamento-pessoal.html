O Departamento Pessoal vive em Projeto Departamento Pessoal/. É a ferramenta mais simples do portal em termos de arquitetura: 3 arquivos (index.html, app.js, styles.css) + 1 arquivo de dados (data/rescisao.js), sem framework/bundler, sem cliente Supabase próprio — o único uso de Supabase é indireto, via portal-auth-guard.js (carrega supabase-config.js e o SDK @supabase/supabase-js@2 só para o guard validar a sessão). Não há nenhuma chamada a supabase.from(...) em nenhum arquivo da ferramenta. É um guia de consulta operacional (roteiro de processos de DP), com todo o conteúdo hardcoded em JS — sem CRUD, sem persistência de dados própria, sem tela de edição. Renderização é innerHTML de template string, igual ao padrão do resto do portal. Diagramas usam Mermaid 10 via CDN (mermaid@10/dist/mermaid.min.js), com mermaid.run() chamado manualmente por diagrama (não startOnLoad).

Arquitetura Geral

Stack e Estrutura de Arquivos

  • index.html — shell único da ferramenta: sidebar (#navTree) + área de conteúdo (#main). Sem rotas, sem outras páginas — tudo é renderizado dentro dessa única página via JS.
  • app.js (IIFE, ~193 linhas) — único script de comportamento. Monta a árvore de navegação a partir de window.DP_CATEGORIAS, renderiza o conteúdo do fluxo selecionado e inicializa o Mermaid.
  • data/rescisao.js — único arquivo de dados hoje. Define window.DP_CATEGORIAS, um array de categorias (hoje só 1: "Rescisão", id rescisao) cada uma com um array de fluxos. Comentário no topo do arquivo diz que o conteúdo foi extraído de documentos Fluxo Rescisão/*.docx mantidos na raiz do projeto como referência (não lidos em runtime).
  • styles.css — visual puro (paleta --brand:#8B3A3A igual à Central do Departamento Contábil), sem lógica.
  • Dependências externas via CDN: @supabase/supabase-js@2 (só para o auth guard) e mermaid@10. Nenhuma outra lib (sem jsPDF/AutoTable — a ferramenta não gera PDF).

Para adicionar uma categoria nova de processo (ex.: Admissão, Férias), o padrão é criar um novo arquivo em data/<categoria>.js que dá push ou concatena em window.DP_CATEGORIAS (ou edita rescisao.js para incluir outro objeto no array), e referenciar o novo <script> em index.html antes de app.js. app.js já é genérico o bastante para múltiplas categorias — a UI de sidebar já trata DP_CATEGORIAS como lista.

Modelo de Dados

Não há tabelas Supabase. A ferramenta não persiste nem lê dado nenhum do banco — é puramente um guia de referência estático, com todo o conteúdo (fluxos, etapas, tarefas, documentos, observações, diagramas) hardcoded em data/rescisao.js e servido como está. O único contato com o Supabase é o SDK carregado para o portal-auth-guard.js validar a sessão do usuário (PortalAuthGuard.init(1)) antes de remover o overlay de "Verificando acesso..." — não há gating de conteúdo por papel/empresa dentro da ferramenta em si; uma vez autenticado, o usuário vê todos os fluxos.

Fluxo Principal

Navegação de categoria → fluxo → renderização de conteúdo + diagrama. Cada clique num item da sidebar re-renderiza inteiramente #main via innerHTML e reprocessa o Mermaid daquele fluxo especificamente (por id incremental mermaid-N, evitando colisão com o diagrama do fluxo anterior que ainda pode estar no DOM até o innerHTML ser substituído).

flowchart TD
    A[Carrega index.html] --> B[PortalAuthGuard.init aguarda sessao valida]
    B --> C[renderNavTree monta sidebar a partir de DP_CATEGORIAS]
    C --> D[Usuario clica numa categoria]
    D --> E[Categoria expande/recolhe classe aberta]
    E --> F[Usuario clica num fluxo]
    F --> G[selecionarFluxo busca objeto fluxo por id]
    G --> H[Monta innerHTML de main com resumo, mermaid bruto e etapas]
    H --> I[mermaid.run renderiza o SVG do fluxograma daquele fluxo]
    H --> J[Listeners de acordeao religados nas etapas]
    G --> K[marcarAtivoNaSidebar destaca botao ativo]

Decisões de Design / Particularidades

  • Mermaid já usado dentro da própria ferramenta — cada fluxo carrega seu próprio texto flowchart TD em data/rescisao.js (campo mermaid), incluindo um caso com nó de decisão (acordo-mutuo não, mas pedido-demissao-desconto-dispensa usa D{Situação do Aviso Prévio} com 3 ramificações rotuladas D -->|A: Desconto total| E). Sintaxe: sem aspas nos rótulos, mas com <br/> dentro dos colchetes para quebra de linha (funciona porque flowchart: { htmlLabels: true } está setado na config do Mermaid em app.js) — diferente da recomendação de "evitar HTML dentro de colchetes" de outras ferramentas do portal; aqui é deliberado e configurado para isso.
  • Tema do Mermaid é customizado via mermaid.initialize({ theme: 'base', themeVariables: {...} }) com as cores da marca (#8B3A3A), igual à paleta de styles.css — não usa o tema Mermaid padrão.
  • mermaid.run({ nodes: [el] }) é chamado passando só o elemento do diagrama recém-inserido (não mermaid.run() global) — evita re-renderizar diagramas de fluxos já visitados que possam ter ficado de alguma forma no DOM, e evita a corrida de "Mermaid tenta renderizar antes do innerHTML terminar".
  • mermaidSeq incrementa a cada seleção de fluxo, mesmo re-selecionando o mesmo fluxo — garante id único mesmo em cliques repetidos, já que o elemento antigo é substituído mas o Mermaid internamente pode cachear por id.
  • Renderização condicional dos cards "Considerações legais" e "Checklist de documentos" — nem todo fluxo tem os dois (ex.: sem-justa-causa-com-aviso não tem observacoes); ausência do campo não gera card vazio, só omite.
  • Todo o roteiro reflete o sistema legado "Domínio" (folha/DP) mencionado nos textos das tarefas (caminhos de menu tipo "Processos > Rescisões > Individual") — é documentação de processo operacional externo ao portal, não de uma tela do próprio Departamento Pessoal.

Dívida Técnica / Pendências

  • Uma única categoria (Rescisão) com 6 fluxos hoje — sem UI de busca/filtro na sidebar; se o conteúdo crescer bastante (novas categorias como Admissão, Férias, Afastamento), a sidebar de árvore simples pode não escalar bem sem paginação ou busca.
  • Conteúdo é só HTML injetado a partir de strings JS — não há sanitização porque o conteúdo é 100% estático/hardcoded pelo próprio time (sem input de usuário), mas isso significa que qualquer novo fluxo adicionado precisa ter HTML válido manualmente verificado (um < ou > solto em algum detalhes quebra o template).
