A Mala Direta tem duas implementações independentes que compartilham o mesmo banco Supabase (projeto principal do portal, tabelas mala_direta_*): a versão web, em Projeto Mala Direta/ — HTML+JS puro, um único index.html de ~255KB (sem build step, sem módulos separados) que concentra CRUD de campanhas/contatos/grupos, o conversor de PDF (pdf.js client-side) e os dois canais de disparo automático (Brevo) e semi-automático (mailto/lote Outlook); e a versão desktop, em Projeto Mala Direta Electron/ — um app Electron enxuto (~3 arquivos) que só lê campanhas já criadas na web e as dispara controlando o Outlook instalado via COM/PowerShell. As duas seções abaixo documentam cada uma; a diferença de mecanismo de envio automático entre elas é o ponto mais importante desta spec.

Versão Web

Stack e Estrutura de Arquivos

  • Projeto Mala Direta/index.html — SPA client-side única: todo HTML de todas as telas (Dashboard, Campanhas, Contatos, Grupos, Conversor PDF, Envios Recorrentes, Configurações) já está no DOM, navegação troca display de seções (showSection()), sem router. JS inline no próprio arquivo, sem módulos ES/bundler.
  • Projeto Mala Direta/styles.css — folha de estilos própria (não reaproveita o CSS geral do portal).
  • Projeto Mala Direta/confirmacao.html — página pública standalone (sem auth) que recebe ?token=&acao= e faz UPDATE mala_direta_envios via cliente Supabase anônimo.
  • Projeto Mala Direta/schema-mala-direta.sql — schema versionado de mala_direta_contatos, _campanhas, _envios, _grupos, _grupo_contatos, _regras + RLS. Não inclui mala_direta_config (tabela chave/valor usada para a config do Brevo — existe no banco mas não está neste arquivo de schema, ver Dívida Técnica).
  • Projeto Mala Direta/conversor-vencimentos/ — ferramenta standalone desacoplada: script Python (pdf_to_excel_vencimentos.py) + wrappers .bat/.sh, roda fora do navegador e gera um Excel. Não é o caminho usado pela tela "Conversor PDF" do index.html, que reimplementa a extração em JS com pdf.js direto no navegador (pdfjs-dist@3.11.174 via CDN, ver Fluxo Principal). Os dois conversores coexistem no repo por motivos históricos.
  • Autenticação via ../portal-auth-guard.js (window.PortalAuthGuard.init(1, {returnAfterLogin:true})), mesmo guard compartilhado do resto do portal; cliente Supabase criado com SUPABASE_URL/SUPABASE_KEY globais definidos por esse script.

Modelo de Dados

TabelaPapel / Colunas-chave
mala_direta_contatosCatálogo reutilizável (nome, email, telefone, empresa, cargo, ativo). RLS: qualquer authenticated tem CRUD total.
mala_direta_campanhastipo_confirmacao (CHECK leitura|interesse|nenhuma), template (texto ou HTML completo — decidido por heurística, ver Decisões), assunto_email, status (rascunho|ativa|encerrada, pouco usado na prática), data_agendamento (preenchida pelo Conversor PDF/Regras). RLS: SELECT livre para authenticated; UPDATE/DELETE só is_admin() OR auth.uid() = criado_por.
mala_direta_envios1 linha por (campanha × destinatário) — é o snapshot do envio, não um FK "vivo" para contato: nome/email/telefone/empresa/cargo são copiados no momento da criação (contato_id é opcional, pode ser NULL para destinatário avulso). mensagem_final guarda o template já com variáveis substituídas. token UUID hex de 32 chars (crypto.randomUUID().replace(/-/g,'')), gerado no front, é a "senha" de acesso à página de confirmação — não há verificação adicional. status_envio (pendente|enviado) e status_confirmacao (pendente|lido|confirmado|recusado) são independentes. RLS tem policy dedicada pro anon: só pode fazer UPDATE se status_envio='enviado' AND status_confirmacao='pendente', e só pode escrever um novo status_confirmacao válido — evita dupla resposta e resposta antes do envio real.
mala_direta_grupos / mala_direta_grupo_contatosAgrupamento N:N simples de contatos, usado só para pré-selecionar destinatários ao montar uma campanha (não persiste vínculo grupo↔campanha).
mala_direta_regrasRegras recorrentes geradas pelo Conversor PDF: tipos (array de tipos de evento reconhecidos), frequencia (semanal|mensal|unica), dia_envio/dia_envio_tipo ('ultimo' para último dia do mês), agrupar_empresa, template, ultima_execucao, metodo_envio (mailto/brevo — não está no schema.sql original, coluna adicionada depois). Execução é sempre manual (usuário clica "Executar" na tela); não há cron/edge function — a regra só dispara um aviso visual quando alguém abre a tela no dia programado.
mala_direta_configTabela chave/valor (chave, valor, atualizado_em) usada só para brevo_key/brevo_nome/brevo_email. Não documentada em schema-mala-direta.sql. A chave de API do Brevo fica em texto puro no banco (mesma categoria de decisão que contabil_mapeamento_bancos em Departamento Contábil) e também trafega para o cliente sem mascaramento (fica no value do input ao abrir Configurações).

Configurações de lote de Outlook (loteMax, loteIntervalo, loteDelay) e o modo de template (texto/HTML) ficam só em localStorage do navegador (md_lote_max, md_lote_intervalo, md_lote_delay, md_modo_html) — não sincronizam entre máquinas/usuários, diferente da config do Brevo que é compartilhada via mala_direta_config.

Fluxo Principal

Conversor PDF → campanha (extração 100% client-side, sem backend):

flowchart TD
    A[Usuario seleciona PDF de Avisos de Vencimento] --> B[pdf.js le paginas no navegador]
    B --> C[Regex por tipo de evento reconhece linhas]
    C --> D[Tabela revisavel: empresa, CNPJ, colaborador, tipo, vencimento]
    D --> E[Aba Agrupar e Agendar: filtra tipos e empresas]
    E --> F{Frequencia}
    F -- unica --> G[Data escolhida manualmente]
    F -- semanal --> H[Semana do dia da semana escolhido]
    F -- mensal --> I[Mes calendario do dia escolhido]
    G --> J{Criar Campanha Agora ou Salvar Regra}
    H --> J
    I --> J
    J -- Campanha Agora --> K[INSERT mala_direta_campanhas + mala_direta_envios]
    J -- Regra Recorrente --> L[INSERT mala_direta_regras]
    L --> M[Aviso na tela Envios Recorrentes no dia programado]
    M --> N[Execucao manual reimporta PDF do dia]

Envio automático via Brevo (executarEnvioBrevo(), linha ~5077) — chamada HTTP direta do navegador para a API do Brevo, sem intermediário no Supabase:

sequenceDiagram
    participant U as Usuario (navegador)
    participant JS as index.html (client-side)
    participant SB as Supabase REST
    participant BR as api.brevo.com

    U->>JS: clica Enviar via Brevo
    JS->>SB: SELECT mala_direta_envios pendentes da campanha
    loop cada destinatario pendente
        JS->>JS: applyTemplate + _buildConfirmButton (token do envio)
        JS->>BR: POST v3/smtp/email (api-key no header, sender, to, htmlContent)
        BR-->>JS: 201 ou erro
        alt sucesso
            JS->>SB: UPDATE mala_direta_envios SET status_envio=enviado
        else falha
            JS->>JS: acumula em lista de erros, segue para o proximo
        end
        JS->>JS: sleep 300ms
    end
    JS-->>U: barra de progresso + toast com total ok/erro

Envio manual via mailto e lote pelo Outlook: window.open('mailto:...') monta um rascunho no cliente de email padrão do SO com destinatário/assunto/corpo (texto) já preenchidos; o corpo HTML não é aceito por mailto:, por isso o modo "HTML formatado" copia o HTML para a área de transferência e pede Ctrl+V manual. O "Envio em Lote" (iniciarEnvioEmLote()) só automatiza a abertura sequencial de rascunhos, respeitando loteMax/loteIntervalo/loteDelay do localStorage — cada rascunho ainda exige clique em Enviar dentro do Outlook; o job roda num objeto de estado global (emailBatchJob) que sobrevive à troca de tela dentro da SPA (mesma aba do navegador), mas é perdido se a aba fechar.

Decisões de Design / Particularidades

  • isHtmlTemplate() decide texto-vs-HTML por heurística de prefixo (trim().toLowerCase().startsWith('<!doctype'|'<html')) — não há coluna própria de tipo; se o usuário colar um HTML sem essas tags no topo, o sistema trata como texto plano e escapa tudo.
  • mala_direta_envios é desnormalizada de propósito (snapshot de nome/email/etc. no momento do envio) — editar um contato depois não altera envios já criados a partir dele, e destinatário avulso funciona sem precisar de linha em mala_direta_contatos.
  • O link de confirmação embutido no HTML (_buildConfirmButton) é montado com URL relativa à própria página (window.location.href menos o querystring), então aponta para onde quer que o index.html esteja hospedado no momento do envio — diferente da versão Electron, que usa uma URL fixa do GitHub Pages (ver seção Desktop/Electron, Decisões).
  • Variáveis de template ({{campo}}) casam por nome de coluna case-insensitive contra as chaves da linha do envio; no preview, uma variável sem valor fica destacada em amarelo (applyTemplateHighlight) em vez de silenciosamente virar string vazia, para o usuário perceber antes de disparar.
  • Envio via Brevo não passa por nenhuma Edge Function do Supabase — é fetch direto do navegador para api.brevo.com com a API key exposta no client-side (qualquer um com acesso ao DevTools da sessão logada vê a chave).

Dívida Técnica / Pendências

  • mala_direta_config (config do Brevo) não está em schema-mala-direta.sql — quem for recriar o banco do zero a partir desse arquivo vai faltar essa tabela; precisa ser extraída do banco vivo antes de qualquer migração.
  • Coluna metodo_envio de mala_direta_regras (referenciada no JS) também não aparece no schema.sql — mesmo tipo de gap.
  • Chave de API do Brevo e senha nenhuma de criptografia: fica em texto puro no banco e é enviada ao client inteira sempre que a tela de Configurações carrega.
  • Progresso de envio em lote (Outlook) só existe em memória JS de uma aba — fechar a aba no meio de um lote perde o acompanhamento (os emails já efetivamente enviados continuam marcados no banco, mas o restante do lote não é retomado automaticamente).

Versão Desktop (Electron)

Stack e Estrutura de Arquivos

  • Projeto Mala Direta Electron/main.js — processo principal: cria a BrowserWindow (contextIsolation: true, nodeIntegration: false) e expõe um único handler IPC, enviar-email-outlook, que é todo o mecanismo de automação do Outlook (ver Fluxo Principal).
  • Projeto Mala Direta Electron/preload.js — ponte contextBridge: reimplementa um client REST mínimo pro Supabase à mão (sbPost/sbQuery/sbPatch com fetch cru, sem @supabase/supabase-js), com SB_URL/SB_KEY (anon) hardcoded no arquivo. Expõe window.electronAPI ao renderer: login, logout, getCampanhas, getCampanha, getEnvios, marcarEnviado, enviarEmail.
  • Projeto Mala Direta Electron/index.html — renderer: tela de login própria (chama electronAPI.login, que faz POST /auth/v1/token?grant_type=password direto, sem passar pelo portal-auth-guard.js do portal web) + lista de campanhas + detalhe/envio. CSS inline no próprio HTML, sem reaproveitar styles.css da versão web.
  • package.json — electron-builder gera instalador NSIS Windows (appId br.com.scont.maladireta); dependências de dev apenas (electron, electron-builder), sem dependências de produção (nem @supabase/supabase-js, o REST é feito à mão).
  • App é somente leitura/disparo em relação ao domínio de campanhas — não cria campanha, contato, grupo, regra nem lê PDF; consome exclusivamente mala_direta_campanhas e mala_direta_envios já populadas pela versão web.

Modelo de Dados

TabelaUso pelo Electron
mala_direta_campanhasSomente leitura: getCampanhas() (select=*&order=created_at.desc) e getCampanha(id).
mala_direta_enviosLeitura (getEnvios(campId), ordenado por nome) e a única escrita do app: marcarEnviado(envioId) faz PATCH status_envio='enviado', data_envio=now() após cada COM .Send() bem-sucedido — mesma tabela e mesmas colunas que a versão web usa, então o status fica sincronizado nos dois lados.

Não há tabela nem coluna própria do Electron — ele não introduz schema novo, só consome o da versão web pela API REST do PostgREST (sem SDK, sem RLS bypass: usa o mesmo anon key + JWT de sessão obtido no login).

Fluxo Principal

Envio automático por destinatário (enviarTodos() no renderer → IPC → main.js → PowerShell → COM Outlook). Este é o mecanismo real, confirmado em main.js: não é uma API de e-mail, é automação de desktop do Outlook instalado.

sequenceDiagram
    participant R as Renderer (index.html)
    participant P as preload.js (electronAPI)
    participant M as main.js (processo principal)
    participant FS as Sistema de arquivos temp
    participant PS as powershell.exe
    participant OL as Outlook.Application (COM)
    participant SB as Supabase REST

    R->>R: monta htmlFinal = template com variaveis + botao de confirmacao
    R->>P: electronAPI.enviarEmail(dest, assunto, htmlFinal)
    P->>M: ipcRenderer.invoke('enviar-email-outlook', dados)
    M->>FS: writeFileSync temp/md_body_TIMESTAMP.html (corpo HTML)
    M->>M: monta script .ps1 (string template, aspas simples escapadas)
    M->>FS: writeFileSync temp/md_send_TIMESTAMP.ps1
    M->>PS: execFile powershell -ExecutionPolicy Bypass -File script.ps1 (timeout 30s)
    PS->>OL: New-Object -ComObject Outlook.Application
    PS->>OL: CreateItem(0) / seta To, Subject, HTMLBody (le o temp html)
    PS->>OL: mail.Send()
    OL-->>PS: sucesso ou excecao COM
    PS->>FS: Remove-Item do html temporario (finally)
    PS-->>M: stdout OK ou stderr com mensagem de erro
    M-->>P: resolve {ok:true} ou {ok:false, erro}
    P-->>R: resultado da invocacao IPC
    alt ok
        R->>SB: electronAPI.marcarEnviado(envioId) -- PATCH status_envio
    else erro
        R->>R: acumula em errosEnvio, segue pro proximo destinatario
    end
    R->>R: sleep(delay em ms, configuravel na tela) antes do proximo

O laço fica inteiro no renderer (for sequencial em enviarTodos()), um IPC roundtrip por destinatário — não há envio em paralelo. O .ps1 é gerado do zero a cada email (arquivo novo com timestamp no nome) e apagado só ao final da execução do PowerShell (fs.unlinkSync(tmpPs) no callback do execFile), enquanto o .html temporário é removido de dentro do próprio script PowerShell (bloco finally).

Decisões de Design / Particularidades

  • Automação COM, não API: o "envio automático" da versão Electron depende de o Outlook desktop estar instalado, configurado com uma conta de email e (na primeira vez, ou conforme política) aceitar o prompt de segurança do próprio Outlook para automação de terceiros controlando o objeto Outlook.Application. Sem Outlook instalado na máquina, o app não envia nada — diferente da versão web (mailto/Brevo), que não depende de nenhum programa externo.
  • Escape de aspas simples na montagem do script PowerShell é manual (s.replace(/'/g, "''")) diretamente na interpolação de string — não há sanitização contra outros metacaracteres do PowerShell (backtick, $); assunto/nome com esses caracteres pode quebrar o script gerado (risco de injeção de comando fraco, mitigado só pelo fato de o conteúdo vir de campanhas já cadastradas por usuários internos autenticados, não de input público).
  • Corpo do email é sempre gravado em arquivo temporário e lido de volta via [System.IO.File]::ReadAllText(...) dentro do PowerShell — decisão deliberada "evita problemas de escape" (comentário no código) por não colocar o HTML inteiro dentro da string do .ps1.
  • CONFIRM_BASE do botão de confirmação é uma URL fixa apontando para https://scontsolucoescontabeis.github.io/scont/Projeto%20Mala%20Direta/confirmacao.html — diferente da versão web, que monta a URL de confirmação relativa a onde o index.html está hospedado no momento (ver seção Web, Decisões). Se o mirror do GitHub Pages sair de sincronia com o deploy real do portal, os links enviados pela versão Electron podem apontar para uma cópia desatualizada da página de confirmação.
  • Login do Electron não usa portal-auth-guard.js nem qualquer guard compartilhado — é uma chamada direta ao endpoint de senha do GoTrue (/auth/v1/token?grant_type=password), com o token de acesso guardado só em memória (variável accessToken em preload.js, perdido ao fechar o app).
  • Intervalo entre emails é configurável na UI (input em ms, persistido em localStorage do Electron, chave md_el_delay) — mesmo padrão de "config só local" da versão web, sem sincronizar com os campos loteMax/loteIntervalo de lá (são localStorages de processos diferentes, nunca se veem).

Dívida Técnica / Pendências

  • Sem paralelismo nem retomada de progresso: se o app fechar no meio do envio de uma campanha grande, é preciso reabrir a campanha e clicar em enviar de novo — como os já enviados ficam marcados no banco (status_envio='enviado'), o app filtra de novo por pendentes e não duplica envio, mas não há fila persistente.
  • URL de confirmação hardcoded (GitHub Pages) é um ponto de acoplamento que só é atualizado editando e recompilando o app — qualquer mudança de domínio/hospedagem do portal exige nova build do instalador Electron para todos os usuários da versão desktop.
