O Simulador de Folha vive inteiramente em Projeto Simulador Folha/index.html — um único arquivo (~3330 linhas: HTML + CSS + JS inline, sem separação em módulos, sem build step). Stack: HTML/CSS/JS puro, cliente Supabase próprio (sbSim = window.supabase.createClient(SUPABASE_URL, SUPABASE_KEY)) usando as credenciais globais do portal (../supabase-config.js, mesmo projeto Supabase principal — não é um dos projetos LIC_URL_A/B). Autenticação/gating de acesso à ferramenta via ../portal-auth-guard.js (PortalAuthGuard.init(1)), igual a qualquer outra ferramenta do portal. Diferente de boa parte do portal, aqui a persistência tem RLS real por usuário (não só filtro client-side) — ver Dados e Persistência. Não há geração de PDF (sem jsPDF): exportação é só CSV via Blob + link de download. Todo o estado das telas (cenários, configurações, cargos) fica em variáveis globais JS (cenarios, configuracoesAvancadas, encargos, cargosPersonalizados) recarregadas do Supabase a cada DOMContentLoaded; não há cache local (sem localStorage).

Estrutura Geral

Stack e Estrutura de Arquivos

  • Projeto Simulador Folha/index.html — arquivo único: 5 abas (Dashboard, Cenários, Comparação, Memória, Configurações) trocadas via mostrarTab() mostrando/escondendo .tab-content, sem roteamento por URL nem recarregamento de página.
  • Sem arquivo JS separado — todo o código está entre <script>...</script> dentro do próprio HTML. Sem framework de componentes: cada aba é montada via template string + innerHTML/insertAdjacentHTML, e os listeners são onclick/onchange inline no HTML gerado.
  • Dependências externas via CDN: @supabase/supabase-js@2 (jsDelivr) e Font Awesome 6.4.0 (cdnjs). Nenhuma lib de PDF/planilha.
  • schema_simulador.sql na raiz do portal (fora da pasta da ferramenta) — único artefato SQL da ferramenta: cria as 4 tabelas sim_* e todas as policies de RLS.

RLS — exceção no portal

Diferente da maioria das ferramentas do portal (onde o isolamento por usuário costuma ser só client-side, com RLS aberta para authenticated), o Simulador de Folha tem RLS real e restritiva nas 4 tabelas: cada policy (SELECT/INSERT/UPDATE/DELETE) resolve usuario_id IN (SELECT id FROM solicitacoes_acesso WHERE email = auth.email()) — em sim_colaboradores a checagem é indireta, via subquery em sim_cenarios. Ou seja, um usuário autenticado só enxerga/edita seus próprios cenários mesmo acessando a API diretamente com a anon key; não depende do front-end respeitar usuario_id nos filtros. getSimUsuarioId() lê auth.userId de sessionStorage.userAuth (o mesmo id de solicitacoes_acesso usado pelas policies) — se essa chave não bater com a sessão Supabase Auth ativa (auth.email()), as queries simplesmente retornam vazio, silenciosamente.

Engine de Cálculo (calcularCenario)

Stack e Estrutura de Arquivos

  • Função pura calcularCenario(colaboradores, regime, faturamento, diasUteis, valeAlimentacao, planosaude, avAlvo, vendaIndividual), linha ~2522 de index.html. Não lê nem grava nada no Supabase — recebe os dados já carregados e devolve um objeto de totais + detalhes[] (1 item por colaborador).
  • Chamada em 3 pontos: criarCenario() (ao salvar/editar um cenário), carregarCenarios() (recalcula todo cenário vindo do banco no load — os totais não ficam persistidos, só os inputs), e salvarConfiguracoesAvancadas() (recalcula todos os cenários já em memória quando os percentuais de encargos mudam).
  • Os totais (custoMensal, encargos, av etc.) nunca são gravados no banco — só os campos de entrada (sim_cenarios/sim_colaboradores). Isso implica que mudar a configuração de encargos/alíquota recalcula retroativamente todos os cenários existentes; não há "congelamento" do cálculo no momento em que o cenário foi criado.

Modelo de Dados

Esta função não persiste nada por si própria — ver tabelas em Dados e Persistência (ela só consome/produz esses registros via as funções que a chamam).

Memórias de Cálculo

Por colaborador, a partir da venda individual (faturamento dividido igualmente entre todos os colaboradores do cenário, calculado fora da função, em criarCenario/carregarCenarios):

vendaIndividual = faturamento / colaboradores.length comissao = vendaIndividual * (colab.comissao / 100) diasNaoUteis = 30 - diasUteis se colab.tipo === 'celetista': remuneracao = colab.salario + comissao baseDSR = comissao senao (comissionado): remuneracao = max(comissao, colab.salario) baseDSR = (comissao > colab.salario) ? comissao : colab.salario dsr = (baseDSR / diasUteis) * diasNaoUteis baseEncargos = remuneracao + dsr encargosColab = baseEncargos * encargosRegime.total

Provisões, por colaborador (FGTS sempre 8% fixo no código, não configurável mesmo para Lucro Presumido):

ferias = baseEncargos / 12 terco = ferias / 3 decimo = baseEncargos / 12 // mesma formula/valor de "ferias" fgts13 = decimo * 0.08 fgtsFerias = ferias * 0.08 fgtsTerco = terco * 0.08 multa40 = (fgts13 + fgtsFerias + fgtsTerco) * 0.40 rescisao = fgts13 + fgtsFerias + fgtsTerco + multa40

Totais do cenário (soma de todos os colaboradores + benefícios agregados):

beneficios = valeAlimentacao * diasUteis * colaboradores.length + planosaude * colaboradores.length custoMensal = remuneracaoTotal + encargosTotal + dsrTotal + feriasTotal + tercoTotal + decimoTotal + rescisaoTotal + beneficiosTotal custoAnual = custoMensal * 12 impostoAnual = (faturamento * 12) * aliquotaTributaria(regime) custoTotalAnual = custoAnual + impostoAnual av = custoMensal / faturamento se av > avAlvo + 0.02 -> statusEficiencia = 'critico' senao se av > avAlvo -> statusEficiencia = 'atencao' senao -> statusEficiencia = 'saudavel'

Percentuais de encargos e alíquota tributária, por regime — vêm de dois objetos globais em paralelo, encargos (efetivamente usado no cálculo dos encargos sociais) e configuracoesAvancadas (fonte da alíquota tributária e dos valores exibidos/persistidos na tela de Configurações). Decisões de Design / Particularidades

  • Dois "defaults" divergentes para Lucro Presumido. O objeto encargos.lucro (usado de fato no cálculo enquanto atualizarConfiguracao() não roda) tem RAT=1,8%/Terceiros=5%/total 34,8% — herdado de antes da feature de configuração existir. O objeto configuracoesAvancadas.lucro (e os value= dos inputs HTML da aba Configurações, e o default do schema_simulador.sql) tem RAT=2%/Terceiros=1,8%/total 31,8%. carregarConfiguracoesAvancadas() só chama atualizarConfiguracao() (que recalcula encargos.lucro.total a partir de configuracoesAvancadas) quando já existe uma linha em sim_configuracoes para o usuário — se data vier null (usuário nunca salvou configuração), a função retorna sem chamar atualizarUIConfiguracao()/atualizarConfiguracao(), então o cálculo de Lucro Presumido roda silenciosamente com 34,8% de encargos enquanto a aba Configurações mostra 31,8% como "padrão". Isso só se resolve quando o usuário visita a aba Configurações e clica em Salvar (ou em qualquer onchange de input lá, que chama atualizarConfiguracao()) pelo menos uma vez.
  • Os totais do cenário nunca são persistidos — só os inputs (sim_cenarios/sim_colaboradores). Toda leitura recalcula via calcularCenario. Consequência: mudar os percentuais em Configurações recalcula retroativamente todos os cenários já salvos (comportamento intencional, documentado no Manual do Usuário), incluindo cenários antigos que foram criados sob outra config.
  • editarCenario(id) remove o cenário do array local cenarios (para preencher o formulário e evitar duplicidade visual) mas não apaga a linha no Supabase. Se o usuário navegar para outra aba/recarregar a página sem clicar em "Criar Cenário" para confirmar a edição, o cenário reaparece ao recarregar (a exclusão local era só de UI) — não há de fato perda de dado, mas o comportamento "sumiu da tela" pode confundir quem só olhar o client-side.
  • FGTS incidente sobre férias/13º/rescisão é sempre 8% fixo no código (não lido de configuracoesAvancadas.*.fgts dentro de calcularCenario, apesar de existir esse campo no objeto) — só o FGTS-encargo mensal (dentro de encargosRegime.total) usa o valor configurável.
  • Cargo é TEXT livre em sim_colaboradores.cargo, mas o valor gravado é o value do <option> gerado a partir do nome do cargo personalizado, normalizado (toLowerCase().replace(/\s+/g,'_')) — não há de-normalização ao exibir de volta; se o cargo personalizado for renomeado/excluído em sim_cargos, colaboradores salvos anteriormente mantêm o slug antigo e gerarOpcoesCargoHtml simplesmente não vai encontrar opção correspondente pré-selecionada.

Dívida Técnica / Pendências

  • Unificar os dois objetos de encargos (encargos e configuracoesAvancadas) e garantir que carregarConfiguracoesAvancadas() sempre chame atualizarConfiguracao() — inclusive quando não há linha salva no banco — para eliminar a divergência 34,8%/31,8% descrita acima.
  • Não há teste automatizado para calcularCenario (diferente de outros módulos do portal, como contabil-diario-util.js, que têm teste Node puro dedicado).
